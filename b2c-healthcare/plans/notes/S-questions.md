# Workstream S: questions and the defaults chosen

| # | Question | Default chosen |
| --- | --- | --- |
| 1 | The agent worktree started at an older commit. | Fast-forwarded to `worktree-b2c-healthcare` as instructed. |
| 2 | "Placement outcome unknown": how does the buyer reach a page when no order id exists? | New route `/order` (no id): "We could not confirm your order", never says "placed", button "Check your orders" to `/account/orders`. Q's place flow (`hooks/use-place-flow.ts`) now goes there when the place request gets no usable answer (`FAILED`: network failure or an answer without a code). Coded failures (502 PLACEMENT_FAILED etc.) still show Q's inline message because the server said the order was not placed. Q's idempotency key (cart + version) means a retry cannot create a second order. |
| 3 | Where do the order types live? | `lib/order-types.ts` (S-owned, client-safe), not `lib/types.ts` (untouched). Mapper in `lib/mappers/order.ts`. |
| 4 | Foreign vs unknown order id. | One query on `id` AND `customerId`; no result = `null` = `notFound()` / 404 `{ error: 'Order not found.' }`. The same helper serves read, cancel and reorder (`getRawOrderForCustomer`). A malformed id never reaches the platform. |
| 5 | Order list size/pagination. | Newest first, `limit 50`, no pagination controls (order-history asks for paging "across the whole history": parked, see S-missed). |
| 6 | Cancelled orders in the list (Q-missed: refused-at-the-last-moment orders stay in commercetools as `mlv-cancelled`). | Shown with a red "Cancelled" badge, not hidden: the buyer was shown an authorization and may have seen a refund. |
| 7 | Timeline for a cancelled order. | "Order received" (done) then "Cancelled" (danger), nothing pending after it. We do not know how far the order got, so no more steps are claimed. |
| 8 | Cancel: order of operations. | (1) transition to `mlv-cancelled` (the platform State machine refuses it after packed-shipped: 400 maps to `too-late`), (2) `restoreAuthorization` (idempotent on the ledger entry), (3) `restoreAllowance` / `restoreRestricted` (no-op hooks for U in `lib/ct/order-cancel-hooks.ts`), (4) per Payment: add a `Refund` transaction in state `Initial` for the authorized amount (skipped when one exists), then void the authorization through `PaymentProvider.release`. A failed release is logged (status only) and does not undo the cancel. Cancelling an already cancelled order succeeds and re-runs steps 2-4, so a cancel that stopped half way is completed by pressing the button again; nothing is restored twice. |
| 9 | Is a `Refund` marker right when the authorization is simply voided (nothing was captured)? | Done as instructed ("mark the payment for refund"); it is the record ops act on if a capture had happened, and the order page reads "Refund requested" from it. Once the PSP/MC moves the transaction to `Success`, the page says "Refunded". Whether a voided, never-captured payment should say "Refund requested" or "Payment released" is an owner question (S-todos). |
| 10 | Cancel while the payment service is not configured. | The route does not depend on it: `PaymentUnavailableError` becomes "no provider", the refund marker is still written, the release is skipped. |
| 11 | Estimate row. | "Today by 8 pm" when the order's shipping method is `mlv-same-day`, else "1-2 business days"; hidden for delivered and cancelled orders. |
| 12 | Shipment state. | Shown as a row from the order's `shipmentState` (Partial reads "Partly shipped: part of your order is on its way and the rest follows"). Per-parcel items and tracking references (spec: Delivery/Parcel/TrackingData) are not modeled: no carrier integration exists. |
| 13 | Reorder semantics. | Not cart replication: each line goes through N's `validateRxSelection` (now, not as at the first order) and the accepted ones through the same `addRxLines` path as "Add to cart" (same-line replacement, platform prices). Always 200 with `{ added, notAdded[{ name, reason }] }`; reasons: no refills, expired, out of stock, unavailable (no longer on the prescription, prescription gone, ceiling/shelf-life refusals, platform quantity limit). The UI names each blocked medication. |
| 14 | Overview "orders" tile. | Unchanged: R's `countOrders` already queries by `customerId`; the list reads the same set. |
| 15 | Returns. | Not built (pharmacy rule); a delivered order says "Medicines that have been dispensed cannot be returned." Scenarios "Return started" and "Refund state visible" are N/A with reasons in the workstream file. |
| 16 | Fixtures. | `MALVA_FIXTURES=1`: `checkout-fixtures.ts` keeps placed orders (on `globalThis`, because route handlers and pages are separate bundles in `next dev`) so `/order/<id>`, the list and cancel can be checked in a browser. Reorder is not available in fixtures (404). Never active in production (same guard as the other loaders). |
| 17 | Shared files touched. | `messages/en-US.json` (+`orders`), `lib/api-paths.ts` (+4), `lib/ct/checkout-fixtures.ts` (+order store), `hooks/use-place-flow.ts` (+1 branch) and its test, `app/[locale]/labs/labs-alias.test.tsx` (the R orders-stub test now mocks session and the order read), `scripts/seed/advance-order.ts`, its test, `fake-root.ts` (+`changeShipmentState`) and `README.md`. `lib/types.ts`, `package.json` and `lib/account-nav.ts` untouched (the Orders entry already existed). |
