# Workstream T: questions and the defaults chosen

| # | Question | Default chosen |
| --- | --- | --- |
| 1 | The agent worktree started at an older commit. | Fast-forwarded to `worktree-b2c-healthcare` as instructed. |
| 2 | Where is the default list and what is its key? The plan says key `mlv-list-<id>`, but a Shopping List key is unique per project and every customer needs "My medicines". | `mlv-list-my-medicines-<customerId>` (created on first save, race-safe: a failed second create reads the winner). Lists the customer creates get `mlv-list-<uuid>`. |
| 3 | "Add all to cart" through commercetools `addShoppingList` (one platform call) or through N's rules? | Through N: `addShoppingList` would put prescription medicines in the cart with no prescription check. The list is walked line by line with `validateRxSelection` (shared core `addPrescribedGroups`, extracted from S's reorder, behaviour of reorder unchanged and its tests green) and `addRxLines`. Prices in the cart are the platform's. The list itself is never changed. |
| 4 | Can any line of a prescription be saved to a list, or only dispensable ones? | Any line of the patient's own prescription (an exhausted one too): the list is a memory aid, dispensability is checked again at "Add all" and named there. |
| 5 | "Save to My medicines" on the Rx card saves which rows? | The selected rows; when none is selected (all rows blocked) all rows. |
| 6 | "Create a first list from the current cart" (spec). | `POST /api/lists { name, fromCart: true }` turns the prescription lines in the cart into list lines (SKU, reference, current price). An empty cart is a readable 422. A plain "Create list" makes an empty one. |
| 7 | List prices at view time. | One `getCatalogBySku` read per page (product projection with the visitor's currency and country), the saved price from the line's custom field; delta shown as "Up/Down $x since you saved it", never repriced silently; a line with no price here is "No longer available to order". |
| 8 | Does the Recurring Order engine let the storefront gate a run? | No hook exists without an API Extension (D-028). The gate runs AHEAD of the run: a daily scheduled check of runs due within 36 h (`checkRuns`) decides with `decideRun` using the DAY OF THE RUN (so a prescription that lapses between check and run counts) and acts on the recurring order: ceiling -> `setOrderSkipConfiguration` (skip that run), expired / missing / no payment method -> pause (resumable after a new prescription), exhausted -> cancel (the series cannot recover). The plan said "lets the order be placed (calls the recurring order's order creation)": there is no such call, the platform creates the order, so "allowed" is only logged. Gap: a run due in the first hours after a fresh Rx change is not intercepted (T-missed). |
| 9 | `decideRun` signature. The plan says `decideRun(recurringOrder, rxState, ceilings)`. | `decideRun({ lines: [{ lineRef, qty, packs, rx, perOrderMax, periodCeiling, usedInPeriod }], today, hasPaymentMethod })`: pure, no commercetools types; the runner builds `lines` (so every case is a table test). Uses N's `checkReplenishmentRun` and `checkCeiling`. |
| 10 | The Netlify function cannot import `server-only` modules. | `netlify/functions/auto-refill-run.ts` is a thin wrapper (schedule `0 5 * * *`) that POSTs to `/api/internal/auto-refill-run` with `x-refill-secret`; the work (decideRun, ledger, refill log) runs inside the Next app. The plan said the wrapper records skips; the app route does, the effect is the same (`malva-refill-log`). Public-trigger guard: Netlify routes no public traffic to a scheduled function; a call that is not a scheduler event must carry the secret; the route itself needs the secret (503 when unset, 401 otherwise) and the run is idempotent (one check per run). A forged `next_run` body cannot start anything the route would not do for the scheduler itself. |
| 11 | Orders the platform generates have no `MLV-` number, no state, no consumed prescription. | The same scheduled function reconciles orders created from a recurring order in the last 5 days: `consumeAuthorization` (idempotent on the order id), `setOrderNumber` from the counter, `transitionState` to `mlv-received` with `force: true` (unverified, T-todos). A refusal at that moment (prescription changed between check and run) only logs: the order exists and was paid (T-missed). |
| 12 | Fixed or Dynamic price selection, per product or project-wide? (spec open question) | Dynamic, set on every recurring line at creation (project-wide), and the page says so in words ("Priced at the catalog price on the day each refill is created"). A Fixed refill would say the other sentence (the mapper and page support both). The two seeded policies have no recurrence-specific prices: the platform falls back to the standard price. |
| 13 | "Schedule changed in place": cadence or a quantity? | Cadence only (`setSchedule`, same recurring order and cart). A quantity is not changeable: one prescription line is one pack by the dispensing rules, so a quantity change would break them. |
| 14 | Source of an auto-refill. | Either a past order (`{ orderId, cadence }`, all its prescription lines, an "Auto-refill this order" control on each order card, shown only when `AUTO_REFILL_ENABLED=true`) or lines of the patient's own prescriptions (`{ rxNumber, lineRefs, cadence }` from the setup form on `/account/auto-refill`). Either way each line is re-validated now; lines that fail are named; a line already in an Active or Paused auto-refill is not added twice. Refills ship `mlv-standard` (the same-day cut-off means nothing on a schedule). The first refill is one cadence after today. |
| 15 | A saved payment method is needed to enable auto-refill. | Yes: the default saved method (else the first) becomes a 100% `Checkout` payment allocation on the recurring Cart (`setRecurringPaymentConfiguration`, public beta, SDK types do not have it yet: sent untyped), so a refill exists only if its payment succeeds. If attaching fails the new recurring order is canceled again. |
| 16 | Recurring carts must not become the shopping cart. | `fetchActiveCart` (O) now filters `origin="Customer"` and ignores a session cart whose origin is `RecurringOrder` (one line each, O's tests green). |
| 17 | Which refills does removing a card affect? | Those whose recurring Cart allocation names the method (Active or Paused). Removal is refused with 409 `REFILL_DEPENDS` and the count until the request is repeated with `confirm=1`, then the card is removed and those refills are paused (a refill that cannot be paid would fail). The scheduled check also pauses a refill whose method is no longer saved. |
| 18 | Resume. | Resume re-checks the prescription for today (`previewDecision`): lapsed / exhausted / no method -> 409 `RESUME_BLOCKED` with the reason in words; a ceiling does not block. Allowed from Paused and Failed. |
| 19 | The "Save this card" checkbox at checkout (T-10). | Not a storefront checkbox: Checkout Stored Payment Methods offer saving and list saved cards inside the widget when the cart carries the `customerId` (O creates carts with it). A storefront checkbox could not make the PSP store a card and would put a consent choice outside the PSP frame. The payment card shows a hint and a link to "Manage saved cards". |
| 20 | Where does a stored card's brand and last four live on the PaymentMethod? | Connector-defined and not documented: `mapDescriptor` reads custom fields `brand`/`last4`/`expMonth`/`expYear` (and `cardBrand`/`cardLast4`/`expiryMonth`/`expiryYear`) and falls back to a display name such as "Visa ending 4242" (T-todos live check). A last four that is not four digits is dropped. |
| 21 | Spec open question: does `setDefault` clear the previous default? | Assumed not (it is a per-method boolean): the adapter clears every other default first, then sets the chosen one (a failure in between leaves no default, the safe state). Live verification is in T-todos; PROJECT-FINDINGS was not edited (needs the live project). |
| 22 | Spec open question: who may remove a card in a business account? | N/A (B2C: the customer owns their cards; business units, net terms / credit line and list sharing are B2C-excluded and not built). |
| 23 | How does a buyer add a card from the payment methods page (spec: "path to add one")? | The empty state points to saving a card while paying (link to the cart). There is no standalone tokenization form: Checkout offers none outside a payment (T-todos: confirm with the owner whether a "setup intent" flow is wanted). |
| 24 | Refund of a payment made with a stored card. | Checkout's automated reversals do not work for stored-method payments (docs). The page says refunds to a saved card cannot be reversed automatically; S's cancel still voids the authorization through `cancelPayment` (live check: whether that works for stored-method payments, T-todos). |
| 25 | Fixture mode. | `loadAccountFixtures` (lib/ct/account-fixtures.ts) gives in-memory Shopping Lists, recurring orders and carts on `globalThis`; the fake payment provider holds saved cards (descriptors only) on `globalThis`; `POST /api/payment-methods/demo-add` (404 unless fixtures) saves a Visa 4242 descriptor.
