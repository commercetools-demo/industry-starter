# Workstream N: questions and the defaults chosen

| # | Question | Default chosen |
| --- | --- | --- |
| 1 | The agent worktree started at an older commit. | Fast-forwarded to `worktree-b2c-healthcare` as instructed. Branch: `worktree-agent-a362ff968097fe992`. |
| 2 | What is "remaining quantity" of an authorization? `Prescription` only has `refillsLeft`. | Remaining units = `refillsLeft` x the line's prescribed quantity. A fill (one order against the prescription) consumes ONE refill, however many of its lines are in that order; no partial supply (Q-038): a request above what remains is refused whole and "N left" is stated (`NO_REFILLS` with `remaining`). |
| 3 | Idempotency of `consumeAuthorization(orderId, lines)`. | Each prescription records the order ids that consumed a refill (`consumedBy`, additive optional field on F's `Prescription`) in the same versioned write as the decrement; the ledger entry (`malva-dispense-ledger`, key = order id, create-only `version: 0`) is written last and its existence means "done". A crash between the two is repaired by the retry; a retry never decrements twice. `restoreAuthorization` removes the id and adds the refill back, then marks the ledger entry `restoredAt` (ceilings ignore restored entries). Validation of every prescription and ceiling happens before the first write, so a refusal consumes nothing. |
| 4 | Unit of the ceilings: units or packs? | Packs. In the seed every RX line quantity equals the pack size (21, 20, 30, ...), so one RX line = one pack = `PACKS_PER_LINE` (1) and the cart quantity for an Rx line is 1. If a line ever needs several packs, `packs` is already carried through `SelectedLine` and the ledger. |
| 5 | What is the per-party, per-period ceiling? The seed only has `maxQtyPerOrder`. | Default: the monthly ceiling equals `maxQtyPerOrder` (`periodCeilingFor`), i.e. at most N packs of the item per patient per calendar month, and the order limit N is the native `maxCartQuantity`. Separate monthly numbers would need a new product attribute (seed change, workstream E). The ceiling belongs to the patient (receiving party), not the account. |
| 6 | Calendar month in which time zone? | UTC (`periodOf` takes the first 7 characters of the ISO instant). The UI says "calendar month". A clinic-zone month is a one-line change in `rules.ts`. |
| 7 | Where do the ceilings read their running total? | `getUsedInPeriod(patientRef, sku, month)` / `getUsedBySku` query the ledger by `value(patientRef=... and period=...)`. Two concurrent orders can both pass the pre-check and both write (the refill decrement is race-safe, the monthly count is not serialized). Acceptable for the demo; a per-patient-month counter object with `version` would close it (N-missed). |
| 8 | Native limit error codes. | Verified in the docs (knowledge MCP): `LineItemQuantityBelowLimit` with `quantity` and `minCartQuantity` (documented sample response); limits are enforced on cart create/update and order creation, not on Order Edits or imports. The upper-bound code is assumed to be `LineItemQuantityAboveLimit` with `maxCartQuantity` (counterpart, not shown in a sample): `mapLimitError` maps both and returns the same `Refusal` shape as the BFF rule. The seed already sets `maxCartQuantity` from `maxQtyPerOrder` (checked by test, no seed change needed). |
| 9 | Custom Object optimistic concurrency. | Reused F's `putObject(..., version)`: a write with a version succeeds only if it matches, `409` otherwise; `version: 0` creates only. Both documented behaviours are modelled by the existing fake; the loops re-read and retry up to 6 times, then `ConcurrencyExhaustedError`. |
| 10 | Short-dated stock: the plan says "own price via a second variant price channel `mlv-short-dated`" but the seed has no such channel or price. | Implemented generically (`shortDatedPriceOf` reads a price whose expanded channel key is `mlv-short-dated`); with no such price, stock below the promise is excluded with a reason (`SHELF_LIFE`, actual expiry stated). Seeding the channel and price is a seed change (E), see N-todos. In the seed, `MED-famotidine-20-mg` (expiry 2026-11-15, promise 30 days) meets its promise until 2026-10-16 and is short-dated after. |
| 11 | "Account minimum excludes unsuitable stock": the per-account minimum is B2C-excluded. | The product promise (`minRemainingShelfLifeDays`) acts as the minimum; the test of that name proves stock below it is excluded with the reason. |
| 12 | The row shows "Minimum N months of shelf life on delivery" for which products? | Only dated products (inventory entry has `expiryDate`); undated goods show no date and nothing is recorded (scenario "Undated goods unaffected"). Days to months: whole months, rounded down, at least 1. |
| 13 | Where does the selected total come from? The guide says totals come from the platform. | The server sends the catalog pack price on every row and the card sums the selected rows with `formatMoney` (integer cents, never `/100`). It is informational; the platform cart is authoritative (workstream O). No separate total endpoint (it would need one call per subset). |
| 14 | Add to cart (`POST /api/cart/rx-lines`) belongs to O. | `lib/ct/prescriptions.ts` exports `validateRxSelection(patient, rxNumber, lineRefs, ctx)` returning `accepted` (with `sku`, `qty`, `packs`, `price`, `perOrderMax`, `periodCeiling`) and `refused` rows. The page calls an injected `onAdd`; `hooks/use-cart.ts` got a tiny additive `useAddRxLines()` placeholder that POSTs `{ rxNumber, lineRefs }` (body, never a URL) to `API_CART_RX_LINES` and revalidates `KEY_CART`. O should replace its body (or fold it into `useCart` as `addRxLines`). Until O ships the route the page shows "We could not add these medications to your cart". The "replacing a line already in the cart from the same prescription and medication" part of the Add to cart scenario is O's. |
| 15 | Signature of `validateRxSelection`. The plan says `(patientRef, rx, lineRefs)`. | `(patient, rxNumber, lineRefs, ctx)`: it also needs the patient name (for the view) and the visitor's locale/currency/country for prices. Unknown and foreign numbers throw the same `RxNotFoundError`. |
| 16 | Patient identity. | No reader of `custom.patientRef` existed, so `lib/ct/patient.ts` (`getPatient(customerId)` -> `{ patientRef, name }`) reads it from the customer. A customer without `patientRef` gets the same not-found as an unknown number. L (booking) may add its own reader; the two are trivially mergeable. |
| 17 | Lookup of malformed input and a missing patient record. | Both are "not found": same 404 body and they count toward the rate limit (like unknown/foreign), so nothing distinguishes the cases. The rate limit is checked BEFORE the lookup, so a limited customer gets 429 even for a number that exists. Rate-limit store outage: errors propagate (500); unlike sign-in it does not fail open, because failing open would allow enumeration. |
| 18 | The not-found text and HTML escaping. | The server's 404 body has the message with the input HTML-escaped (and capped at 40 characters, control characters removed). The page does not render that string; it composes the message itself from its i18n catalog with the typed input as a React text node (escaped by React), so the visible text is the same without double escaping. |
| 19 | Quick-picks. | The server page reads the patient's own prescriptions (numbers and dates only) and hands them to the client component; a failure to read them hides the shortcuts only. `GET /api/prescriptions` exists for other callers. A quick-pick runs the normal lookup (a successful one costs nothing against the rate limit). |
| 20 | Dev fixtures for browser checks. | `MALVA_FIXTURES=1` now also feeds `/prescriptions` (`lib/ct/rx-fixtures.ts`, loaded through `loadRxFixtures` with the same production guard as K's loader): seed patients and prescriptions, full stock, in-memory rate limiter. Fixture customer ids are `fixture-<slug>`; `scripts/dev-session.ts` signs a session cookie for them from `SESSION_SECRET` (never stored). Nothing is written in fixture mode. |
