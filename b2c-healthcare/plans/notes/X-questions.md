# Workstream X: questions and the defaults chosen

| # | Question | Default chosen |
| --- | --- | --- |
| 1 | Which resources does `dataErasure=true` cover? | Verified against docs.commercetools.com/api/gdpr (2026-10-08): Customer, Cart, Order, Payment, Review, ShoppingList, DiscountCode, CustomObject, BusinessUnit, Quote, QuoteRequest, StagedQuote. Message is removed with its resource; there is no DELETE for it. `GDPR_KINDS` / `ERASABLE_KINDS` in `scripts/privacy/lib.ts`. |
| 2 | RecurringOrder is not on the `dataErasure` list (auto-refill, workstream T). | `erase-patient` cancels it (`setRecurringOrderState canceled`, reason `erasure`) and reports it under `notErasable`; subject-access includes it. Live follow-up in X-todos. |
| 3 | The docs say the Customer DELETE no longer removes carts (carts are preserved). | Erase deletes orders, carts, payments, ... explicitly, the customer last. |
| 4 | Which predicate finds each kind? | Cart/Order `customerId="x"`; Payment, Review, ShoppingList, Quote, QuoteRequest, StagedQuote `customer(id="x")`; BusinessUnit `associates(customer(id="x"))`; Customer `id=` or lower-cased `email=`; Message `resource(id in (...))` over every id found; DiscountCode: the page says "query CartDiscounts ... where Cart Predicate contains the Customer ID", so cart discounts and discount codes are read and filtered in memory on `cartPredicate` containing the id (no `like` predicate assumed). Predicates are written from the API's field names, not run against a live project (no credentials). |
| 5 | Payments with no customer reference (tender payments) are missed by the customer predicate. | Payments referenced by the customer's carts and orders (`paymentInfo.payments`) are added to the set. |
| 6 | How are custom objects tied to a person? | `scripts/privacy/inventory.ts`: `patientRef` for rx, lab, credential, dispense ledger, allowance, allowance ledger, booking; guest bookings by `guest.email` (as typed and lower-cased); `rl-<customerId>` for the rate limiter; cart id prefix for `malva-order-attempt`; recurring order ids for `malva-refill-log`; the booking's slot claim by its derived key. `rl-login-<hash>` buckets (hash of email and client address) cannot be resolved to a person and are only removed by retention. A drift test fails when a container is added to `lib/ct/custom-objects.ts` without an inventory row. |
| 7 | A real erase run needs a safety catch. | Beyond `--dry-run`, a real run needs `--confirm <customerId>` (the id the run resolved). |
| 8 | Retention periods not in the plan: cancelled patient booking, order attempt, refill log, stale slot claims. | Cancelled patient booking: reason and phone replaced/removed 90 days after the visit (booking row kept). Order attempt locks: 30 days. Refill log: 180 days. Slot claims: a day after the slot. Constants in `RETENTION` (`scripts/privacy/inventory.ts`); owner to confirm at SO-04. |
| 9 | Retention de-identification for a patient whose clinical basis lapsed (e.g. erased customer with leftover objects). | Not built separately: erasure removes those objects; retention handles guests and housekeeping only. |
| 10 | Where does the retention function get its credentials? | Netlify function builds a client from the storefront `CTP_*` variables (same as `reload-allowances`); that client needs custom-object manage scope (X-todos). No seed project-key guard in the function (it must run on the real storefront project); the guard stays in the CLI. |
| 11 | "Add owner sign-off row SO-04 evidence" (X-08): `TODO-MANUAL-TESTING.md` is not mine to edit. | Evidence is in `docs/privacy-inventory.md` section 6 (decision record); the owner or Claude adds the SO-04 row from it. |
| 12 | Static scan (b) scope: the task says `lib/` and `app/api`. | Widened to lib, app, components, hooks, context, netlify and scripts/privacy; the name list is `HEALTH_NAME` in `static-scans.test.ts` (sig, diagnosis, condition, result, reason, lab, rx, medication, booking, symptom, allergy, dose, email, phone).
