# Follow-up AA (full commercetools Checkout): questions and the defaults chosen

Sources: commercetools documentation (Checkout Browser SDK, "Order creation edge cases", "Payment lifecycle", "Extend the Checkout functionality", Payment Intents API), read through the knowledge MCP and the `commercetools-checkout` skill. Nothing was run against a live project (no credentials).

| # | Question | Default chosen |
| --- | --- | --- |
| 1 | Who handles address and delivery in the full Checkout? Complete Checkout normally collects the address and shipping method itself. | Smallest change that keeps the design's three-card page: **our address and delivery cards stay and set the cart** (as before, with `shipping-methods/matching-cart`, the 14:00 same-day cut-off and the totals re-read). The button "Continue to payment" runs the gate and then mounts `checkoutFlow` in the Payment card. Checkout is expected to find address and method on the cart; if the Application still shows its own address / shipping steps, the buyer confirms the same data (live check AA-L2). Alternative not chosen: delete our two cards and let Checkout own them. |
| 2 | Application type: Complete Checkout or Payment Only? | **Complete Checkout** (the only mode in which Checkout creates the order, D-034). The browser calls `checkoutFlow`, not `paymentFlow`. |
| 3 | How does our `MLV-` number reach an order Checkout creates? | `finalizeOrder` sets `orderNumber` after the order exists, only if unset (counter `malva-counter/order-number`, optimistic concurrency), together with the state `mlv-received`. Checkout also supports `metadata.futureOrderNumber` on the session (the number is then on the order from the first moment); not used, because that needs a reserved number per prepare (gaps when a buyer leaves), see AA-missed 3. |
| 4 | How is "once per order" kept when three callers may finalize (browser callback, lazy read, subscription route)? | A record per order in `malva-order-attempt` (key `fin-<orderId>`: pending / done / refused) taken create-only; a concurrent caller gets `IN_PROGRESS`, a repeat gets the same answer with `replay: true`; a pending record older than 2 minutes is taken over. Every step is itself idempotent (ledger keyed by order id, allowance draw keyed by order id, number only if unset, state only if unset), so a crash is finished by the next caller. Lock freed on unexpected errors. The retention job already deletes `malva-order-attempt` entries after 30 days (X). |
| 5 | How does a missed browser callback (tab closed, network lost) get finalized? | (a) Reading the order finalizes it: `getOrderForCustomer`, `getRawOrderForCustomer` (cancel, reorder) and `listOrdersForCustomer` finalize any order that still lacks its number or state. (b) Optional `POST /api/internal/order-created` guarded by `ORDER_FINALIZE_SECRET` (header `x-order-secret`), accepting `{orderId}`, a commercetools message body or a Pub/Sub push envelope; it is for a Subscription on `OrderCreated` delivered by a Connect event app or a queue consumer (commercetools Subscriptions cannot call a plain HTTPS URL). Not created by us: owner decision whether to wire it. (c) `/order?orderId=<id>` (the Application's Payment return URL) redirects to `/order/<id>`. |
| 6 | Allowance and health-account (restricted) tender with Checkout creating the order. | Their Payments are put on the cart in `prepareCheckout` **before** Checkout runs and the session is created for the **card remainder** (`cardDue`); the draw from the allowance and the Charge records on the tender Payments happen in `finalizeOrder` (idempotent on the order id). Whether Checkout really collects only the remainder when other Payments are already on the cart is **not documented** (the gift-card connector path is the documented way to take partial value). Safeguard built: if the card payment Checkout authorized or charged differs from the plan, `finalizeOrder` refuses (`FUNDING_CHANGED`): the order is cancelled, the card payment is given back through Checkout and nothing is drawn, so there is no double charge. If the live check AA-L4 shows Checkout ignores the tender Payments, the options are: (i) model the allowance as a gift-card Connector, (ii) turn the allowance / health-account off for card orders. Owner decision then. |
| 7 | An order that the allowance and the health account cover completely (no card amount). | Checkout has nothing to authorize, so the **storefront creates the order itself** (`POST /orders` from the cart, no number) and finalizes it in the same call. The one remaining storefront order creation. |
| 8 | Dispense refusal at the last moment (the prescription changed between the gate and the order, or two orders raced). | The order exists and was paid, so it is cancelled (`mlv-cancelled`), the card payment is given back through the seam (cancel the authorization, or refund if something was captured), nothing is consumed, the record is `refused` and stays so. The page says the prescription can no longer be filled and the payment was released. |
| 9 | Cancel and refund (S) and the owner's QR-002 wording. | `cancelOrderForCustomer` still sets `mlv-cancelled` and restores the refill, allowance and restricted value (internal tenders keep their own `Refund`/`Success` record). The CARD payment goes through the `PaymentProvider` seam only: `release` (Payment Intents `cancelPayment`) when only authorized, `refund` (`refundPayment`) when a `Charge` succeeded; our own `Refund/Initial` marker on the card Payment is **removed**. A payment that already carries a `CancelAuthorization` or `Refund` transaction is not asked again. Wording: **"Payment released"** when no capture exists, **"Refund requested"** while a `Refund` is Initial/Pending and **"Refunded"** at Success (`RefundStatus` gained `released`; the cancelled order in fixtures says "Payment released"). |
| 10 | Capture. | Not modelled by the storefront (D-035). Capture when you decide (Merchant Center order > Payments, the Stripe dashboard, or Payment Intents `capturePayment`); the README says how. The demo never captures. |
| 11 | Browser message names. | `checkout_completed` with `payload.order.id` is from the SDK docs; `payment_started`, `payment_cancelled` and the error `payment_failed` are carried over from workstream Q and unverified live. The server never trusts the message beyond the order id: ownership is checked and everything is read from the platform. A completion message with no order id sends the buyer to `/order` (the order list finds it). |
| 12 | What if the completion call gets no usable answer? | The order exists in that case (Checkout made it), so the buyer goes to `/order/<id>`, which finalizes lazily and states the true status; never to "pay again". A `DISPENSE_REFUSED` answer is shown on the checkout page instead. |
| 13 | The cart changes after the gate (second tab). | Not blocked: Checkout verifies its own payment amount against the cart. Lines added later keep their add-time rx fields but have no N-09 line record (no `dispensedQty`); `finalizeOrder` re-checks the ledger (refills) but not the per-order ceilings. Listed in AA-missed 5. The page drops the prepared session whenever the amount or delivery changes and the gate runs again. |
| 14 | Demo provider. | Still dev-only (`MALVA_FIXTURES=1`, never in production). "Place order" runs `prepare` (the same gate on the in-memory cart), then `demo-authorize` (the stand-in for Checkout: records the demo authorization and **creates the order** in the fixture shop, unnumbered), then the same `POST /api/checkout/complete` the browser SDK would call. `finalizeFixtureOrder` is idempotent on the order id like production. |
| 15 | T (auto-refill, stored methods) and U (funding, credentials). | T: no code change. Generated recurring orders are still numbered and consumed by `reconcileGenerated`; `finalizeOrder` uses the same idempotent ledger and "number only if unset", so a lazy read of such an order is safe. `consumeLinesOf` (auto-refill-run) is now shared by both. Stored methods use the unchanged `PaymentProvider` methods. U: the credential and cost-share checks moved with the gate (`prepareCheckout`); tests keep their scenarios. Shared files touched are listed in AA-missed. |
