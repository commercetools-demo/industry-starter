# Workstream P: questions and the defaults chosen

| # | Question | Default chosen |
| --- | --- | --- |
| 1 | The workstream design says removing the default "promotes the next saved or leaves none"; the P-02 task says "removing default promotes next"; the address-book spec scenario "Default address removed" says no address is marked default and none is promoted silently. | The spec wins: removing the default leaves no default (the page shows a note, checkout must ask the patient to choose). Only the first address of an empty book becomes the default automatically. The browser recipe line was corrected. |
| 2 | "Validation cannot resolve the address" without a provider (Q-042). | A static first-three-ZIP-digits to state table. A state/ZIP mismatch is a warning: the server answers 200 `{status:'needs-confirmation', warning:{fields, nearestState}}`, stores nothing, and the form offers "Save anyway" which resubmits with `confirmed:true`. Prefixes not in the table (military, territories, a few exceptions such as 733xx) never warn, or may warn wrongly; the patient can always save. |
| 3 | Phone format. | US only: 10 digits, or 11 starting with 1, optional `+1`; stored as `+1XXXXXXXXXX`. No NANP area/exchange rules. Phone is required. |
| 4 | How are addresses added to the customer? | `addAddress` with a generated `key` (`addr-<uuid>`), then `addShippingAddressId` and optionally `setDefaultShippingAddress` by `addressKey`, in one update. Billing addresses/defaults are not touched (no billing UI). All addresses on the customer are listed, even ones not in `shippingAddressIds`. |
| 5 | Removing the default address. | `setDefaultShippingAddress` (no address) first, then `removeAddress`, in one update, so the outcome does not depend on how the platform treats a dangling default. |
| 6 | Version conflicts. | `updateCustomer` (new `lib/ct/customer-update.ts`) re-reads the customer, plans the actions from it, posts, and retries once on 409. Unknown address id: `AddressNotFoundError` -> 404 `Not found.` (same for another customer's id, since the customer is always the session's). |
| 7 | Where does J's `changePassword` UI call go? | The profile page posts to J's `/api/account/password`; no new password route. The name change is a new `PATCH /api/account/profile` (`setFirstName`/`setLastName`, never `changeEmail`). The email is shown read-only. |
| 8 | Page frame before workstream R. | Both pages sit under `(protected)` with `PageHead` plus a plain container; no `account/layout.tsx` was created, so R's add of one will not clash. |
| 9 | Shared files touched. | `lib/types.ts` (+`Address`, `AddressInput`), `lib/api-paths.ts` (+address and profile paths), `lib/cache-keys.ts` (+`KEY_ADDRESSES`), `messages/en-US.json` (+`account.addresses`, `account.profile`), `hooks/sign-out.ts` and its test (also clears `KEY_ADDRESSES`, so a shared browser never shows the last patient's addresses). |
