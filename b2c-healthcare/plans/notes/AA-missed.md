# Follow-up AA: gaps and things to know

1. **Unverified against a live Checkout.** Complete Checkout's behaviour with a cart that already has an address, a shipping method and other Payments (allowance, health account) is not documented in what was read; the build is defensive (AA-questions 1, 6) but only a live run settles it (AA-todos L2, L4). The safeguard (refuse and give the card back when the card amount differs from the plan) protects against a double charge; it cannot make Checkout take a partial amount.
2. **Fully covered orders are created by the storefront** (nothing to authorize), so one place still calls `POST /orders`. It is idempotent (a lost answer finds the order by cart id; `finalizeOrder` is keyed by order id).
3. **Order number gaps.** `finalizeOrder` takes the number after the order exists, so a number is only used for a real order. A crash between taking the number and `setOrderNumber` (a few ms) leaves a gap; the next run takes a new number. Harmless. `metadata.futureOrderNumber` on the Checkout session would show the number from the first moment (and in the PSP dashboard) but needs a reserved number per prepare; not built.
4. **Lazy finalize cost.** Reading an order or the order list runs `finalizeOrder` only for orders without a number or state; a finalized order costs nothing extra. Any order without a number or state is finalized, including orders not made by the storefront (seed orders, recurring orders): for those it adds a number and the state and consumes lines that carry prescription fields, exactly what T's `reconcileGenerated` already does (both are idempotent on the order id).
5. **Cart changes after the gate.** Not blocked. A line added in a second tab after `prepare` has no N-09 line record (`dispensedQty`, `authorizationParams`) and its per-order ceiling is not re-checked at finalize (only the refill ledger is). Checkout's own amount check catches a changed total. A stronger design would lock the cart (a custom cart state or a Cart Freeze) between the gate and the order.
6. **Finalize reads limits from the catalog again** (`consumeLinesOf` of workstream T: per-order maximum and the monthly ceiling come from `getCatalogBySku` at finalize time, not from what the gate saw). A catalog change between the two could refuse an order that was paid; the refusal path (cancel + give the card back) covers it.
7. **Refund for a card payment is asked, not tracked by us.** If `refundPayment` fails (Checkout down) the failure is logged (status only) and the cancel still stands; pressing "Cancel order" again re-asks (no `Refund` transaction exists yet). The order page shows "Payment released" for a cancelled order whose card payment was only authorized, even if the cancel request to Checkout has not yet succeeded; ops reconcile from the Payment's transactions (no `CancelAuthorization`).
8. **Capture is nobody's job in the storefront** (D-035). Nothing captures on `mlv-packed-shipped`; the authorization will expire at the PSP if nobody captures. A capture trigger (state change or `advance-order`) is a follow-up if the demo must show settled money.
9. **A wholly refunded or released order with an allowance share:** the allowance returns at once; the page's tender rows state it. A mixed order whose card share is only released shows "Payment released" (the internal tenders are not part of the refund wording).
10. **The "Totals moved after authorization" scenario of Q no longer exists** (the amount is compared before Checkout starts; the code `TOTALS_MOVED` is kept for the gate). `PAYMENT_REQUIRED` and `PAYMENT_DECLINED` codes are no longer produced by the server (a declined card is Checkout's own message, or the SDK's `payment_failed`, which the page shows as the declined message); the codes stay in `PlaceOrderFailure` for the messages table.
11. **Subscription not created.** The route exists and is tested; creating the `OrderCreated` Subscription and its consumer (Connect event app) is not done (needs the project).
12. **Shared files touched:** `lib/types.ts` (+`PrepareResult`), `lib/api-paths.ts` (session and place replaced by prepare and complete), `lib/order-types.ts` (+`released`), `lib/mappers/order.ts` (`refundOf` now reads card payments only), `messages/en-US.json` (+`continueToPayment`, `continueHint`, `refund.released`; two sentences reworded), `lib/ct/auto-refill-run.ts` (`consumeLinesOf` exported), `lib/ct/checkout-provider.ts` and `lib/checkout/*` (provider seam), `lib/ct/orders-read.ts` (lazy finalize), `lib/ct/order-cancel.ts` (cancel through Checkout), `.env.example` (additive: `ORDER_FINALIZE_SECRET`, scope comments), `docs/deploy.md` (+1 row), `README.md` (payment lifecycle section), `playwright.config.ts` (port from `PORT`), test helpers `test/fake-shop.ts`, `test/checkout-flow.ts`. The files `app/api/checkout/session/route.ts` and `app/api/checkout/place/route.ts` (and their tests) are deleted.
13. **Chrome DevTools MCP not used;** the browser path was exercised by the Playwright e2e in fixtures mode only. The real Checkout form cannot render without the Application.
