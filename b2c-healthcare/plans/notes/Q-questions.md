# Workstream Q: questions and the defaults chosen

| # | Question | Default chosen |
| --- | --- | --- |
| 1 | The agent worktree started at an older commit. | Fast-forwarded to `worktree-b2c-healthcare` as instructed. |
| 2 | No Checkout Application or Stripe account exists (OA-04) and there are no credentials. | The real adapter (`lib/ct/checkout-provider.ts`) is written to the documented Sessions and Payment Intents APIs behind the `PaymentProvider` interface and is unit-tested with an injected `fetch`. A dev-only fake (`lib/checkout/fake-provider.ts`) serves tests and `MALVA_FIXTURES=1`; it is loaded only through `loadFakePaymentProvider` (null in production). The Payment card shows "DEMO payment (no PSP configured)" when it is used. Without `CTP_CHECKOUT_APP_KEY` the real path answers 503 "Payment is not available right now." and no order can be placed. |
| 3 | Who creates the order in Checkout payment-only mode? The SDK docs show `checkout_completed` carrying an order id; the plan says the storefront creates the order (MLV number, line records, consumption). | Followed the plan: Checkout only authorizes, the storefront creates the order. The server never trusts a browser message: `placeOrder` reads the Payment from the cart. If the Application also creates orders, `placeOrder` finds the cart `Ordered` and returns that order. To be confirmed live (Q-todos 1). |
| 4 | What does the Place order button do with the real widget? | It is the SDK's custom payment button (`data-ctc-selector="paymentButton"`); the widget's `payment_completed`/`checkout_completed` message triggers `POST /api/checkout/place`. In the demo build the click calls the demo authorize endpoint, then place. |
| 5 | Payable amount: `totalPrice` or `taxedPrice.totalGross`? | Gross when the platform has taxed the cart (US prices are tax-exclusive; 0% today, D-033), else `totalPrice`. Taken in `lib/mappers/checkout.ts`, never computed. |
| 6 | The three plan endpoints do not include a read for the page. | Added `GET /api/checkout` (recalculate, re-validate lines, delivery options). Also `POST /api/checkout/demo-authorize` (404 unless the fake provider is loaded). |
| 7 | Task order: Q-05 needs the counter of Q-08. | Q-08 was done and committed before Q-05. |
| 8 | When is the address applied to the cart? | Explicitly: the card is prefilled (cart address, else default address, else blank with the account name) and "Use this address" sets it. Until then delivery options, payment and Place order wait. The address is NOT added to the address book. No state/ZIP mismatch warning in checkout (format validation only; the address book has the warning). |
| 9 | After an address change the delivery method may no longer match (same-day outside NY/TX/IL). | The server re-selects standard when the current method is no longer offered; when nothing is offered the answer is 422 `NO_DELIVERY_METHOD` with the state, and the page withdraws the options and disables Place order. |
| 10 | Idempotency design. | Key = session cart id + cart version shown on the page (`<cartId>_<version>`). A create-only Custom Object (`malva-order-attempt`) is the lock: pending (a concurrent second request gets `IN_PROGRESS`, 409), created (resumes consumption), done (replay returns the same order), refused (stays refused). Retryable failures delete the lock. Pending older than 2 minutes may be taken over. Also: if the cart is already `Ordered`, the order found by `cart(id=...)` is returned. |
| 11 | When is the authorization released? | When the cart total differs from the authorized amount (stale), when order creation or the line-record write fails, when the order number cannot be taken, and when the prescription refuses at the last moment. Not released when the order exists. Always before telling the buyer "your payment was released". A failed release is logged (status only) and does not hide the real outcome. |
| 12 | Prescription refuses at consumption although checks passed (race). | The order already exists, so it is cancelled (`mlv-cancelled`), the payment released, and the attempt stays `refused` (a retry answers the same). The cancelled order remains in commercetools. |
| 13 | Consumption interrupted after the order exists (network). | The attempt stays `created`; the answer is `IN_PROGRESS` ("already being placed"); the same key resumes and finishes (the ledger is idempotent on the order id). A resumed run rebuilds the ledger input from the order lines, without re-checking ceilings. |
| 14 | Same-day method chosen before 14:00, placed after. | Refused at placement as `NO_DELIVERY_METHOD` (the method must still be one `matching-cart` returns and the cut-off must not have passed). |
| 15 | Line record fields (N-09) on the order. | Written to the cart lines (`setLineItemCustomField` x3 per line) just before order creation and copied by the platform onto the order lines: `dispensedQty`, `authorizationParams` (JSON, refills before this order), `suppliedLots` (`[]`). The three fields were added to the `mlv-rx-line` seed type (and its test). |
| 16 | The credential checks of U. | U is not built; `placeOrder` re-runs `validateRxSelection` only. U adds its check at the same place (`prepareLines`). |
| 17 | Shared files touched. | `package.json` + lock (+`@commercetools/checkout-browser-sdk`), `messages/en-US.json` (+`checkout`), `lib/types.ts` (+checkout types), `lib/api-paths.ts` (+6), `lib/cache-keys.ts` (+`KEY_CHECKOUT`), `hooks/sign-out.ts` and its test (clears `KEY_CHECKOUT`), `.env.example` (+`CTP_CHECKOUT_APP_KEY`, `SAME_DAY_NOW_OVERRIDE`, scope `manage_checkout_payment_intents`), `lib/ct/custom-objects.ts` (+`orderAttempt`), `lib/ct/fixtures.ts` (+2 loaders), `lib/ct/cart.ts` (`fetchActiveCart` exported), `lib/ct/cart-fixtures.ts` (+`clearCart`), `scripts/seed/data/types.ts` and `data.test.ts` (+3 line fields), `README.md` (+section). |
| 18 | Capture. | Authorization only in v1 (Q-Q-1): capture on `mlv-packed-shipped` is out; manual capture/refund is in the README. If the Stripe sandbox needs auto-capture for the demo the owner decides. |
