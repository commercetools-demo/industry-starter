# Security review of the portal and storefront (workstream X-14)

Reviewer: J24 (the author of the X changes; a second reader is M-X-03). Method: manual review of every `app/api/**` route (inventory in `plans/evidence/X/route-inventory.md`), the session and cookie code, the Contentools proxies, the headers and the build gates, plus the generated and attack tests. The `security-review` skill was not run on a branch diff: the work is uncommitted on a shared branch and the skill needs a committed diff; run it after the lead commits (add the result below).

Severity scale: high = data of another user or store can be read or changed, or a secret leaks; medium = a control can be bypassed under conditions; low = hardening.

| # | Finding | Severity | Status |
| --- | --- | --- | --- |
| 1 | No same-origin check on any state-changing route: a cross-site form or `text/plain` fetch could ride the Lax session cookie (top-level navigation POSTs are not blocked by Lax in some browsers for the first two minutes). | medium | Fixed: one gate in both `proxy.ts` (D5): Origin must equal Host, or Sec-Fetch-Site same-origin or none; JSON or multipart only (415 otherwise). One documented exemption: the storefront shop-as hand-off form post, whose single-use signed token is the credential. Tests `origin.test.ts`, `proxy.api-gate.test.ts`; curl evidence `csrf-curl.txt`. |
| 2 | The storefront Contentools proxy forwarded every request header except a short deny list (for example `x-forwarded-*`, `x-http-method-override`) and passed upstream 3xx (with `Location`) and 5xx bodies to the visitor. | medium | Fixed: header allow-list, 3xx and 5xx become `502 UPSTREAM_ERROR`, `location` and `www-authenticate` dropped. The H test that pinned the redirect pass-through was updated. |
| 3 | The portal proxy `upload-file` accepted any file type up to 11 MB (HTML, script, executable, SVG with script) and stored it in the Contentools object store. | medium | Reverted by owner decision: the portal no longer inspects the file; Contentools decides what it accepts. Request size cap 5 MB remains. |
| 4 | The portal sent no Content-Security-Policy, no `nosniff`, no frame protection, no referrer or permissions policy, no `noindex`. The storefront had a CSP but none of the other headers, and its `frame-ancestors 'self'` would have blocked the portal preview. | medium | Fixed: portal CSP (`lib/csp.ts`) and headers; storefront gets the static headers and `PORTAL_ORIGIN` in `frame-ancestors`; `poweredByHeader` and browser source maps off; `robots.txt` disallows all on the portal. |
| 5 | Page routes answered PUT, PATCH and DELETE like GET. | low | Fixed (405 in `proxy.ts`). TRACE is refused by Next itself with a generic 500 (nothing echoed). |
| 6 | No JWT canary or release switch: nothing proved the Contentools token never reaches a browser or a release config. | low | Fixed: `CONTENTOOLS_JWT_CANARY` (ignored in production without `ATTACK_MODE=1`), `check-no-attack-mode.mjs`, a JWT-shape scan in `check-bundle-secrets.mjs` (both apps, `.next/static` and `public/`). |
| 7 | The portal had no production gate for the on-screen password reset (the storefront had one). | low | Fixed: `portal/scripts/check-demo-reset.mjs`, wired into `check` and `verify:build`. The reset itself stays an accepted demo risk (Q-X05). |
| 8 | No inventory proving every route has an access rule, and no test proving a refusal happens before any commercetools call. | low | Fixed: `route-policy.ts` in both apps, `check-route-policy.mjs` gate, generated tests with trapped SDK clients (portal 278 cases). |
| 9 | While a seller shops as a customer, the storefront account routes allow writes (password, e-mail, delete, payment methods) and return unmasked profile data (Q-V25). | high (to the customer's account, needs an Admin of the store who is already trusted to shop as that customer) | Open, deferred: the patch is written in the X workstream file ("Deferred to after Q") and applies once J23's work is committed. |
| 10 | Rate limiters (storefront) key on the first `x-forwarded-for` value; the portal has no limiter. | low | Accepted gap (D9, Q-X09), host check in Z. |
| 11 | npm audit: `braces` (high, build-time CLI) and `uuid` (moderate), no fix. | low | Accepted, see `plans/notes/audit.md`. |
| 12 | `script-src 'unsafe-inline'`, `style-src 'unsafe-inline'`, portal `img-src https:`. | low | Accepted, documented in `lib/csp.ts` (Q-X12). |
| 13 | The Merchant Center users with API-client rights are trusted (no API Extension layer, Q-X01 obsolete). | info | Accepted by design. |

Checked and found sound (no change needed): session cookie flags (HttpOnly, SameSite=Lax, Path=/, Secure in production) and forgery (alg none, wrong secret, altered claims, truncated, expired, unknown claims dropped) in `session-forgery.test.ts`; sign-in builds a fresh session instead of extending the old one (fixation); the admin client is imported only from the allowed folders (`admin-client-imports.test.ts`) and price writes all pass `setStandalonePrice` and `assertValidPrice` (`rule-callers.test.ts`, `prices.single-writer.test.ts`); strict zod schemas on price bodies; the tailored image URL intake (https only, private and link-local addresses refused, byte validation); theme CSS built from allow-lists only; JSON-LD escapes `<`; no `dangerouslySetInnerHTML` of user text; shop-as token checks (60 seconds, single use, audience, store) in V's tests; open-redirect guards for `next`; error responses carry no stack or upstream text.

Open high findings: 1 (number 9), deferred with the patch ready. Everything else is fixed or accepted with a reason.
