# Workstream M: Product detail page

**Depends on:** L (and through it E, F, I, J): `mapProductSummary`, `getListingProjections`, `searchParts`, `ProductCard` parts, `useAddToCart`, `POST /api/cart/lines`; I (`useStorePicker`, pickup logic, store settings); J (`FitBanner`, `FitBadge`, `getActiveVehicle` with range keys, `groupRangesForDisplay`, `vehicleInRange`).
**Implements:** `cs/design-product-detail-page` (primary).
**Skills:** `commercetools-storefront` (`b2c/product-detail.md`, `core/product-detail.md`, `core/data-loading.md`), `commercetools-platform` (product projections, in-store endpoints), `commercetools-commerce-patterns` (catalog architecture, product tailoring, price selection, Product Discounts).
**Apps and paths:** everything below lives in `b2b2c-automotive/storefront/`. Run commands from that directory.

## 1. Goal

The page answers three questions without leaving it: does it fit my vehicle, what does it cost me here, and when can I have it. Route `/[locale]/[store]/p/[slug]`. It shows the reseller's tailored name and description (never tailored part number, fitment or specifications), the fit banner for the active vehicle, price with old price and "Save {amount}", stock at the selected branch with address and "Change store", a shipping line, quantity, a "Subscribe and save" option for subscribable parts, and Add to cart, specifications, compatible vehicles, "Often bought together", and the seller's returns line.

## 3. Design decisions already taken

| # | Decision | Source |
| --- | --- | --- |
| D1 | Product data comes from the in-store ProductProjection endpoint (`apiRoot.inStoreKeyWithStoreKeyValue({ storeKey }).productProjections().get({ queryArgs: { where: 'slug(<locale>="<slug>")', ... } })`), which applies the store's product selections and Product Tailoring. Zero results means `notFound()`. | docs "Product Search" (tailoring is only in the in-store projection); `design-product-listing-page` L-R1; design-spec platform note "Reseller text maps to product tailoring" |
| D2 | Part number, fitment and specifications are read from the master (non-tailored) projection (`apiRoot.productProjections().withId`), never from the tailored one, so tailoring can never change them even if the API allowed tailored attributes. Name, description and images come from the in-store projection. Attribute names are the seed's: `part-number`, `oem-numbers`, `fitment-keys`, `universal-fit`, `quality-tier`, `position`, `warranty-months`, `size-spec`, `recurring-eligible`. | `design-product-detail-page` M-R5; `seller-portal/design-product-info-tailoring` (locked fields); `seed/src/data/product-types.ts` |
| D3 | Old price exists only when the selected **standalone** price carries a Product Discount (`discounted` on the `StandalonePrice`): old price is `value`, current is `discounted.value`, chip "Save {old minus current}" (Q-M01). | `design-product-detail-page` M-R1; commerce-patterns discount stacking; owner-answers Q-003 |
| D4 | **All prices are standalone** (owner answer Q-003): the price is `selectStandalonePrice(prices, { currency, country, channelIds: [branchChannelId, retailChannelId] })` from L's `lib/ct/prices.ts`, which prefers the selected branch's price, then the store retail channel price (`mau-dist-north` / `mau-dist-south`), then the channel-less Malva base price (EUR/DE, USD/US); no `priceCurrency/priceCountry/priceChannel` projection arguments. No price means "Price unavailable" and a disabled Add to cart; never zero. | L D4, D12 |
| D5 | **The branch can change the price as well as stock and pickup** (owner answers Q-005, Q-I04). Changing store refreshes server data (price, stock, pickup) with `router.refresh()`, not a full reload; client state (quantity, chosen subscription frequency) survives. | I D6; `design-product-detail-page` M-R2 |
| D6 | **A non-fitting part can be added to the cart with a warning** (owner answer Q-M02, matches the plan): the danger banner and "View fitting alternatives" link are the warning, and the status panel after adding repeats "This part may not fit your {vehicle}"; a line item is never blocked by fit on the PDP. | owner-answers Q-M02 |
| D7 | Description is rendered as plain text paragraphs, never as HTML; the fitment disclaimer (`pdp.fitDisclaimer`) renders under the description always (a superset of "when tailored"). | `design-product-detail-page` M-R5; XSS safety |
| D8 | Add-to-cart feedback is an inline `role="status"` panel under the button with "Continue shopping" and "View cart"; no mini-cart drawer (not designed). | design.md section 6; I D9 |
| D9 | Sticky mobile buy bar, image zoom, video, reviews list, Q&A are not built (design gaps). Thumbnails do switch the main image (placeholders in the design). | `design-product-detail-page` Gaps |
| D10 | Single-variant parts are the norm; if a product has several variants a `<select>` "Option" chooses by `?sku=`. | this plan |
| D11 | Compatible vehicles come from the master `fitment-keys` **year ranges** (`parseFitmentKey` and `groupRangesForDisplay` from J): rows read "Volkswagen Golf · 2012–2019 · 2.0 TDI, 1.4 TSI"; the active vehicle's row is highlighted when its year is inside a range (`vehicleInRange`); `universal-fit` parts show "Fits all vehicles" instead of a list. | J §4.4; owner-answers Q-J03 |
| D12 | Returns line: "Sold and fulfilled by {reseller}. {days}-day returns at any counter." `days` from the store setting `returnWindowDays` of custom type `store-settings` (seeded as 30; returns are accepted 30 days from delivery, Q-Q01), default 30 when absent. | `design-product-detail-page` M-R4; owner-answers Q-Q01 |
| D13 | **Subscriptions are sold** (owner answer Q-Q06): a part with `recurring-eligible = true` shows a "Subscribe and save" option (one-time purchase or subscribe, and a frequency chosen from the project's recurrence policies `mau-rp-monthly`, `mau-rp-quarterly`, `mau-rp-half-yearly`). Subscribing adds the line with `recurrenceInfo { recurrencePolicy, priceSelectionMode }` (N-03); the recurring order is created by commercetools Checkout (O). `priceSelectionMode` is `Dynamic` (each renewal uses the then-current standalone price; constant `SUBSCRIPTION_PRICE_MODE` in `lib/subscriptions/config.ts`). The option is hidden when `SUBSCRIPTIONS_PURCHASE_ENABLED=false`, which O sets to false at OA-05 time if the installed Stripe connector cannot process recurring orders (stored payment methods). | owner-answers Q-Q06; docs "Recurring Orders in Checkout" |

## 4. Data contract

As L (section 4) plus: images on variants; `warranty-months` (number) and `size-spec` (text) shown in the specification table; `recurring-eligible` (boolean) and the three seeded recurrence policies; for subscribable parts a standalone price may carry `recurrencePolicy` (a subscribe price); M-00 checks with `read_standalone_prices` whether the seed has any and records it (if none, the subscription uses the normal selected price). "Often bought together" has no related-products attribute in the seed (no `related-skus`; a seed request, section "Seed requests"): M-08 derives related items from the same category (fallback) and switches to `related-skus` only when the seed adds it; record which in `mcp-checks.md`. Compatible vehicles: the seed's `fitment-keys` are one key per generation and engine (13 generations, so at most 13 grouped display rows for any part); the long-list case (more than 20 rows) therefore exists only as a fixture. Store settings from I; `returnWindowDays` (Number, 30) on type `store-settings`. Product Tailoring: the seed has 5 `product-tailoring` documents (3 in the north store, 2 in the south store; text and images, published at once, Q-T06); if the one you need is missing, test with fixtures and note it. Prices and discounts as seeded: Malva base, retail and branch standalone prices; product discounts (autumn filter promotion -10 % on Filters, north brake week -8 % on Brakes, south battery bonus) give `discounted` on the selected standalone price.
