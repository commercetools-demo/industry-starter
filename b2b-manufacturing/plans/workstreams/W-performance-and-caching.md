# Workstream W — Performance and caching verification

**Depends on:** V
**Implements:** (none — cross-cutting; proves `malva-data-loading` and the performance scenarios of `malva-homepage`)
**Skills:** commercetools-storefront (`core/performance.md`), commercetools-platform

## Design
Prove, with numbers, that public pages are static/ISR and fast, and that nothing per-visitor leaks into them.
- Build output: `npm run build` route table: public routes `○`/`●`, portal and API `ƒ`; `scripts/check-routes.mjs` (G) is the gate.
- Lighthouse (mobile emulation, throttled) on `/en-US`, `/plumbing`, `/waste-management`, one detail page, `/about`, `/request-a-quote`: performance ≥ 90, a11y ≥ 95, best-practices ≥ 95, SEO ≥ 95; LCP ≤ 2.5 s, CLS ≤ 0.05, INP ≤ 200 ms on the dev machine production build.
- Image handling: hero priority with `sizes`, other images lazy with width/height; image URLs are stored clean (`next.config.ts` remote patterns); total transfer budget homepage ≤ 1.5 MB.
- Network: no per-user request on public pages except `/api/quote-list` and `/api/auth/me` after hydration; the commercetools API is never called from the browser.
- Caching: `Cache-Control`/ISR revalidation values documented; `unstable_cache` TTL table respected; the Product Search call count per page render ≤ 2.
- Report `plans/evidence/W/report.md`.
