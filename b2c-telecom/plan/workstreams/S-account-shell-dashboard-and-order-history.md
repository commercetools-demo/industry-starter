# S — Account shell, dashboard and order history

**Specs:** `account-and-self-service` (shell and navigation; its two address scenarios are implemented by T and listed here with their S-level test, see Design 1), `account-dashboard` (all 3 scenarios), `order-history` (all 3 scenarios; the B2B parts are excluded, see Excluded)
**Depends on:** L, M, R · **Unblocks:** T, U, V · **Decisions:** D-005, D-012, D-013, D-021, D-023, D-030, D-040, D-050, D-053, D-059
**Owner prerequisites:** OA-02, OA-03 (the QA order script and every live check) · **Skill refs:** `commercetools-storefront` (account pages, orders), `commercetools-platform` (order queries), `commercetools-commerce-patterns` (recurring orders)

## Goal
A signed-in customer opens `/account` and sees their account, monthly bill, next bill date, current contract and the Broadband Facts labels of their plans (from the snapshot stored on the order), with explicit empty and unavailable states; they can page through all their orders, open an order, print a receipt, and "buy again". A script creates realistic QA orders so these pages can be checked before checkout (U) exists.

## Design

### 1. Scope and routes (all under `app/[locale]/account/`, server components, never cached)
| Route | What |
| --- | --- |
| `/account` | Dashboard (design `design/specs/account.md`) |
| `/account/orders` | Order list: status filter, pagination 10 per page |
| `/account/orders/[orderNumber]` | Order detail; `not-found.tsx` for missing or not-owned orders |
| `POST /api/orders/[orderNumber]/reorder` | "Buy again" (new S route; V owns the other `/api/orders/[orderNumber]/*` routes) |
`/account/addresses`, `/account/payment-methods`, `/account/lists*` are T's pages; S provides the shell and the navigation links to them (they 404 until T ships; the links are plain navigation, not a failure of S). Every S page calls `requireCustomerPage(locale, '<its own path>')` from R (`lib/auth/guard.ts`); there is **no layout-level guard** and no pathname header. The shared layout `app/[locale]/account/layout.tsx` renders `AccountShell` only (navigation rail), so T and V pages get the same frame.

`account-and-self-service` is an umbrella: its pages are built by S (dashboard, orders), T (address book, payment methods) and W (contact, FAQ), and the error pages by I. Its two scenarios are address behaviours implemented by T's address book; S lists them in its table with the **shell-level test** that proves the dashboard reflects them (default address shown, empty address state with a way to add one). T's own table covers the add/remove behaviour.

Planner defaults for open questions: "which account data is personal and which shared company data" → all account data is personal to the customer (B2C, D-005). "Who owns the outstanding balance" → there is no balance panel (B2B, excluded); the **Monthly bill** is computed from the customer's own active orders, not from a finance system. "Invoice documents" → none (D-059); the printable receipt replaces them. "Cost center" → not applicable.

### 2. Data: what comes from where (D-021: holdings = orders and recurring orders)
Everything comes from the customer's commercetools **orders** (`Order`) and **recurring orders** (`RecurringOrder`); never from the cart.
- **Orders list/detail** (`lib/ct/orders.ts`, `import 'server-only'`): `GET /{projectKey}/orders` with `where: customerId="<id>" and recurringOrder is not defined`, `sort: createdAt desc`, `limit: 10`, `offset`, `withTotal: true`. Orders **generated** by a Recurring Order (`Order.origin = RecurringOrder`, `Order.recurringOrder` set; verified in OAS `api-Order-read`) are **not listed** (Planner default: the monthly bills are not "orders" the customer placed). S-02 checks the predicate against the live project; if `recurringOrder is not defined` is rejected, filter `origin = "Customer"` instead and record it in `PROJECT-FINDINGS.md`. Order by number: `GET /orders/order-number={orderNumber}`; **ownership is checked in `getOrderForCustomer(orderNumber, customerId)`** (returns `null` unless `order.customerId === customerId`); pages and routes use only that function.
- **Recurring orders** (summary only): `GET /{projectKey}/recurring-orders` with `where: customer(id="<id>")`, `limit: 100`, fields used: `id`, `recurringOrderState` (`Active|Paused|Expired|Canceled|Failed`), `nextOrderAt`, `expiresAt`, `originOrder.id`. Used for the **next bill date** (earliest `nextOrderAt` of `Active` ones) and to drop contract rows whose origin order has only `Expired`/`Canceled` recurring orders. S-02 first verifies `apiRoot.recurringOrders()` exists in the installed SDK (`@commercetools/platform-sdk` ^8); if it does not, stop and ask. S does not depend on L's code for these reads (own function `getRecurringSummaries(customerId)`).
- **Order status** (`lib/mappers/order.ts`, pure): `orderState = Cancelled` → `cancelled`; `shipmentState = Delivered` → `delivered`; `shipmentState = Shipped` → `shipped`; `orderState = Complete` → `completed`; `orderState = Confirmed` → `processing`; `orderState = Open` → `placed`; else `unknown` (raw states kept). Tag tones: placed, processing, shipped → `--color-pink-*` (action family); delivered, completed → `--color-brand-*`; cancelled, unknown → neutral.
- **Order line classification** (no extra catalog call): `kind` from the line's variant attribute `offer-kind` (`base-package|addon|equipment|device|bundle`) when present, else from `productKey` with a fixed prefix table (strip `malva-offer-`): `cable-`, `wireless-` → internet plan; `phone-nova-` → device; `phone-` → phone plan; `router-`, `mesh-`, `modem-`, `5g-gateway` → equipment; `spotify`, `appletv`, `applemusic`, `netflix`, `disneyplus`, `secure`, `device-protect`, `cloud-` → add-on; anything else → `other`. `family` (for the contract "Type" column): internet plan → "Cable internet" (productKey starts `cable-`) or "Home wireless" (`wireless-`); phone plan → "Phone plan"; add-on → "Add-on"; equipment → "Equipment"; device with installments → "Device installments", lease → "Device lease". Term from variant attribute `contract-term` (`month-to-month|12-months|24-months`) when saved to the line item; S-01 checks a live order, and if the attributes are **not** saved (`savedToLineItem` is false by default), records it in `QUESTIONS.md` for G (blocking only the Term column, which then shows "—").
- **Acquisition of device lines** (Q is not a dependency): read line custom fields `acquisitionMode`, `acquisitionTermMonths`, `acquisitionEndDate` into `OrderLineAcquisition` in S's own mapper section. S never infers a mode from a price.
- **Order custom fields** (type `malva-order`, G): `serviceStartDate` (Date; falls back to the order date), `priceSchedule` (JSON string, L's record; parsed with L's `PriceSchedule` type from `lib/pricing/schedule.ts`; invalid JSON → `null`), `labelSnapshot` (JSON string written by U at order placement: `{ "<lineItemId>": BroadbandLabelData }`, where `BroadbandLabelData` is the prop type of M's `components/label/BroadbandLabel.tsx` exported from `lib/pricing/label.ts`; parsed defensively by `parseLabelSnapshot`, never throws), `cancellation`, `returnRequest` (V's; S ignores them except showing the status).
- **Snapshot rule:** the labels on the dashboard and on the order detail are **only** the stored snapshot, never rebuilt from the live catalog, so a later price change cannot alter the disclosure the customer signed. A plan line without a snapshot (older orders) shows the note "Label not available for this order." instead of a rebuilt label.

### 3. Dashboard (`/account`) per `design/specs/account.md` and `account-dashboard`
Layout: breadcrumb "Home / My account"; H1 "Hi, {firstName}" (Exo, `--text-5xl`... use `--text-4xl`); **summary row** `grid-template-columns: repeat(auto-fit, minmax(300px, 1fr)); gap: var(--space-7)`:
1. **ACCOUNT** — email, "Account no. {customerNumber} · Active" (customer number from R's registration; "—" when absent).
2. **MONTHLY BILL** — current monthly total (Exo 700 `--text-4xl`), "Next bill {date}".
3. **DELIVERY ADDRESS** (undrawn addition: Junior design choice, D-068) — default shipping address in two lines, link "Manage addresses" → `/account/addresses`; empty: "No address saved yet." + link "Add an address".
4. Honey card (`--color-surface-brand`) "Want to change something?" with buttons "Browse plans" (→ `/shop/phone-plans`, brand-950 pill) and "Log out" (calls `POST /api/auth/logout`, then `router.push('/')`).
Below: **Recent orders** (3 newest: number, date, status tag, total, link; "All orders" link), **Current contract** (H2 + bordered table, radius `--radius-xl`, horizontal scroll under 640 px, `min-width: 640px`, header row `--color-neutral-50`, Exo 600 `--text-xs` caps columns ITEM, TYPE, STARTED, TERM, PRICE (right aligned), grid `2fr 1.2fr 1.4fr 1.4fr 1fr`; footnote "The early-termination fee is shown on each plan's Broadband Facts label."), **Your plans** (H2 + grid `repeat(auto-fit, minmax(min(100%, 400px), 1fr))` of `BroadbandLabel`, one per active plan; add-ons have no label), and an empty slot component `DashboardExtras` (renders `null`; T fills it with the saved lists preview).
**Data rules:**
- Contract rows: for every order that is not `Cancelled` and whose recurring orders (if any) are not all `Expired|Canceled`, each **recurring line** (line with `recurrenceInfo`, or service line) becomes a row: Item = line name (device: "Nova Pro 256 GB, Black"), Type = family, Started = `serviceStartDate` (formatted with `Intl.DateTimeFormat(locale, { dateStyle: 'medium' })`, e.g. "Mar 12, 2026"), Term = "24 months · ends Mar 12, 2028" / "Month-to-month" / device "24 months · ends {endDate}", Price = monthly amount × quantity incl. "/mo". Rows sorted by Started descending, then Item. A line with `kind = equipment` and no recurrence (purchased router) is not a contract row. Device lines bought outright are not rows.
- Monthly bill = Σ of the **current period amount** of the rows not yet ended: `line.total` unless the order has a `priceSchedule`, in which case L's period lookup for today gives the amount (use L's exported function from `lib/pricing/schedule.ts` that returns the amount payable on a date; if L names it differently use L's name; the contract is "Money for date D, or null when the schedule does not cover D", and `null` → fall back to `line.total` and show nothing extra). Empty → "$0.00" with "No upcoming bills."
- Next bill date = earliest `nextOrderAt` among `Active` recurring orders of the customer, formatted `dateStyle: 'medium'`; none → "No upcoming bills."; recurring reads failed → "Next bill date unavailable" (amount still shown).
**Empty states (spec "Nothing yet on the account": nothing is hidden):** Recent orders "No orders yet." + button "Browse plans"; Current contract "You have no active services yet." + button "Browse plans"; Your plans "Your plan labels appear here once you have an active plan."; Monthly bill "$0.00 / No upcoming bills."; Delivery address as above.
**Unavailable states (spec "One backing service down"):** each panel is its own async server component inside its own `<Suspense fallback={<PanelSkeleton/>}>`; each wraps its data call in `withTimeout(promise, PANEL_TIMEOUT_MS = 4000)` (`lib/account/with-timeout.ts`) and a `try/catch` that renders `<PanelUnavailable titleKey=... />` (`role="status"`, text "This section is unavailable right now. Try again in a moment.") instead of throwing; the other panels render normally. Panels sharing the orders query (Recent orders, Current contract, Your plans, Monthly bill amount) share one `cache()`-wrapped call per request (`getCustomerOrdersCached`), so they fail together by design; the recurring-orders query is separate (Monthly bill's next-bill date); the customer query is separate (Account, Delivery address).
**Session no longer valid (spec):** `requireCustomerPage(locale, '/account')` redirects to `/<locale>/login?returnTo=%2F<locale>%2Faccount` **before** any data is read; nothing about the account is rendered.
**Logout** clears caches through R's `useAuthMutations().logout`.

### 4. Order list (`/account/orders`)
H1 "Your orders", status chips (`filter chip` component of I): "All", "Open" (`orderState in ("Open","Confirmed")`), "Completed" (`orderState = "Complete"`), "Cancelled" (`orderState = "Cancelled"`), selected via `?status=open|completed|cancelled` (default all) and `?page=N` (1-based; invalid → 1). Table columns: Order (number, link), Placed, Items (summary "Cable 500, Apple TV+ +1"), Status (tag), Total ("{one-time} today · {monthly}/mo"), 10 rows per page, "Previous/Next" and "Page 1 of 2", pagination over **the whole history** (`offset = (page−1)×10`, `withTotal`). Below 640 px rows stack as blocks (label left, value right). Empty: "No orders yet." with "Browse plans"; empty after a filter: "No orders match this filter." with a "Show all" link.

### 5. Order detail (`/account/orders/[orderNumber]`)
Heading "Order {orderNumber}", placed date (`dateStyle: 'medium'` + time `short`), status tag, "Service start {date}" (D-023: order date + install lead time, from the stored field), then:
1. **Items** table: image/name, type, quantity, unit price, line total; recurring lines show "/mo"; device lines add a sub-row "Pay in full" / "Installments, 24 months" / "Lease, 24 months" and the end-of-term fact when `acquisition.endDate` exists ("Final payment {date}" / "Return by {date}"); add-ons/equipment show their parent plan name when `parentLineItemId` is set.
2. **Totals**: "Due at order" (one-time lines + first payment of recurring lines as stored: `order.totalPrice`) and "Monthly after that" (Σ recurring lines), per-acquisition-mode lines only if the order has more than one mode ("Pay in full {amount}", "Installments {amount}/mo", "Lease {amount}/mo").
3. **Price schedule** (only when `priceSchedule` parses): M's `components/bundle/PriceSchedule.tsx` with the stored schedule, introduced by the heading "Your agreed prices".
4. **Broadband Facts** (only plan lines with a snapshot): `BroadbandLabel` from the snapshot, heading "Broadband Facts at the time of your order".
5. **Delivery address** (`shippingAddress`) and "Delivery status" text = the status tag label. **Tracking: Planner default — no carrier tracking links in v1** (no fulfillment integration, D-059); the shipment status text is all that is shown. **Receipt: Planner default — a "Print receipt" button** (`window.print()` with `@media print` rules that hide the header, footer, navigation rail and buttons, set the table to black on white and show "Receipt for order {orderNumber}" and the customer's name); no PDF and no invoice (D-059).
6. Actions: **Buy again** (not shown for orders in `cancelled` state), and the extension slot `components/account/OrderActions.tsx` (renders `null`; V fills it with "Cancel order" and "Return a device"). 
Not owned / missing order: `notFound()` (HTTP 404) rendering `not-found.tsx` of the segment: heading "We could not find that order", text "It may belong to a different account.", button "All orders"; **no order data is fetched for display before ownership passes** (spec "Detail of an order not theirs").

### 6. Reorder ("Buy again") — spec "Reorder with an unavailable item"
`POST /api/orders/[orderNumber]/reorder` (same-origin check from R, `requireCustomerApi`): loads the order via `getOrderForCustomer` (404 `ORDER_NOT_FOUND` otherwise); calls commercetools **Replicate Cart** (`POST /{projectKey}/carts/replicate`, body `{ reference: { typeId: 'order', id } }`; replication is the documented reorder mechanism, [docs](https://docs.commercetools.com/learning-model-b2b-commerce/implement-b2b-purchase-flows/the-b2b-cart); a replicated cart always has the current product data) → compares lines by `sku`: any original line whose SKU is missing from the new cart, or whose recurrence info did not survive (original had `recurrenceInfo`, new line has none), is **removed from the new cart** and reported → sets the new cart as the session's cart → returns `200 { cart: Cart, unavailable: { sku: string; name: string; reason: 'not-available' | 'recurrence-lost' }[] }`. The previous active cart is **not** deleted (kept by commercetools; M's cart reader always takes the session's `cartId`). The UI shows a banner on `/bundle` via query `?reordered=<n>` and, when `unavailable` is not empty, a dialog listing each item with the text "These items could not be added: {names}." before navigating to `/bundle`. M's cart repricing and compatibility rules apply on the next cart read (nothing to do here). S-09 verifies the replicate response shape against OAS `api-Cart-write` / the docs and records it.

### Pitfalls
- Order and recurring-order reads are **session specific**: no `unstable_cache`, no `revalidate`, no shared fetch cache; export `dynamic = 'force-dynamic'` on the account pages.
- A date-only custom field (`serviceStartDate`) must be parsed as a UTC date (no time-zone shift): format with `timeZone: 'UTC'`.
- `Order.customerId` is absent for guest orders (D-035): they belong to nobody and never appear.
- Orders generated by recurring orders must not show up as duplicates in the list or the contract.
