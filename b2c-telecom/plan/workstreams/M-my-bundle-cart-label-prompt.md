# M — My bundle (cart), Broadband Facts label, discount prompt

**Specs:** `cart-management` (all 3 scenarios), `cart-page` (all 3 scenarios), `broadband-facts-label` (all 6 scenarios; the account-page scenario is built here as a reusable component that S mounts), `discount-activating-offer-prompt` (all 6 scenarios)

**Owner prerequisites:** none (live checks need OA-02; the Gate 2 spike result from L must be APPROVED before M-04) · **Skill refs:** `commercetools-storefront` (cart, `core/cart.md`), `commercetools-commerce-patterns` (discounts, recurring)

## Goal
A visitor (anonymous or signed in) can build "My bundle": add plans, add-ons, equipment and handsets with the right recurrence, change phone-line quantity (1-5), remove lines with their dependents, apply a discount code, see engine-calculated totals after every change, read each plan's Broadband Facts label and price schedule before checking out, and be shown the one offer that would unlock a discount they can really get. Blocked adds say exactly why.

### Cart concept: one commercetools cart per market
- Created lazily on the first add (no cart for a visitor who only browses). Draft: `{ currency, country, locale, taxMode: 'Platform', inventoryMode: 'None' /* D-019 */, anonymousId | customerId (from the session), customerGroup (if signed in: group key from the session), origin 'Customer', deleteDaysAfterLastModification: 90, custom: { type: { typeId: 'type', key: 'malva-cart' }, fields: {} } }`. No Store (D-058).
- Anonymous: cart has `anonymousId` from E's session; the cart id lives in the session cookie (`session.cartId`; read E's `lib/ct/session.ts` for the real field names). Signed in: `GET /carts/customer-id={id}` (most recently modified active cart) when the session has no `cartId`.
- A cart whose `currency` differs from the market currency is **ignored, not converted** (a cart cannot change currency). Switching region creates a new cart on the next add; the old one stays (expires after 90 days). (Planner default; same behaviour as the grocery project.)
- **Merge on sign-in:** R's login route passes `getSignInMergeArgs(session)` from `lib/ct/cart.ts` to the commercetools sign-in call: `{ anonymousCart: { typeId: 'cart', id }, anonymousCartSignInMode: 'MergeWithExistingCustomerCart' }` (fields verified in the CustomerSignin schema) and stores the returned cart id in the session. M never calls sign-in itself. After a merge, line ids of merged-in lines may change, so `normalizeCart` (below) runs on every `GET /api/cart`.

### `lib/ct/cart.ts` (`server-only`) [SKILL: commercetools-storefront]

The `fn` of `withCartRetry` always receives the **fresh** cart (grocery lesson: never pass a version captured earlier). Every update returns the new cart; routes return `mapCart(returned cart)` and never patch local state.

**`addOfferLine(cartId, { offer, variant, quantity, parentLineId, required })`** (`lib/ct/cartDrafts.ts` builds the drafts; the same builder is used by the prompt probe cart):
1. Plan/add-on/equipment-rental/device-financed lines (recurring variants): `addLineItem { sku, quantity, recurrenceInfo: recurrenceInfoDraft(lineRecurrence(kind, term)) /* L */, custom: { type: { typeId: 'type', key: 'malva-line-item' }, fields: { offerKey, parentLineItemId? } } }`. One-time variants (equipment purchase, outright device): same but **no** `recurrenceInfo`. (If the L spike chose fallback F1, one-time lines are created with `addCustomLineItem` instead: `{ name: {en-US, de-DE}, slug: sku, quantity, money: variant one-time price, taxCategory, custom }`; the branch is selected by `lib/config/cart.ts` constant `ONE_TIME_AS_CUSTOM_LINE_ITEM` which L-09's result sets: `false` for A and A-prime.)
2. After the update, for every line just created with recurrence call L's `assertRecurringPrice(line, policy, sku)`. If it throws, immediately `removeLineItem` that line (second update) and answer 422 `RECURRING_PRICE_MISSING` (logged as `[catalog-gap] offer=<key> sku=<sku> reason=no-recurring-price`).
3. A plan whose `buildSchedule` returns `ok:false` is removed again and answered 422 `SCHEDULE_NOT_PRICEABLE` (scenario "Period with no price" of L).
4. A plan whose label cannot be built (`buildLabel` returns `missing`) is removed again and answered 422 `LABEL_DATA_MISSING` with `details.missing` (scenario "Required data missing"); the gap is **reported** by a server log line `[catalog-gap] offer=<key> sku=<sku> missing=<fields>` (D-059: no external channel). Order: the label and schedule are checked **before** the add using the offer facts (no commercetools write), so no line is created and removed; the checks in 2 are the only ones needing the created line.
5. **Parent links (D-026):** every add-on/equipment line carries `parentLineItemId`. `parentLineId` is provided by the client; if omitted the server picks the only plan line that the guard says accepts it; if zero or several candidates exist answer 422 `PARENT_REQUIRED`. Dependents are always added **after** the plan in a second update of the same `withCartRetry` call (the plan's new line id is needed).
6. **Required equipment defaults (D-025):** after adding a plan whose guard result lists `required` (J `requiredEquipment`: kinds the plan requires, resolved to the cheapest compatible equipment offer and variant), add each as a line with `parentLineItemId = plan line id` and `requiredEquipment: true` in the mapper (detected because the guard listed it; stored as custom field `offerKey` only; M-04 test fixes how `requiredEquipment` is recomputed on read: an equipment line whose offer is in the plan's required-kinds and whose `parentLineItemId` is set). The buyer may later remove or replace it; if removed the plan gets a blocking issue until another is chosen (J revalidation).
7. **Activation fee:** if `offer.activationFee` has `centAmount > 0` add `addCustomLineItem { name: { 'en-US': 'Activation fee', 'de-DE': 'Aktivierungsgebuehr' }, slug: ACTIVATION_FEE_SLUG_PREFIX + offerKey, quantity: <plan quantity>, money: activationFee, taxCategory: { typeId: 'tax-category', key: ACTIVATION_FEE_TAX_CATEGORY_KEY } }`; if a custom line item with that slug already exists only change its quantity (`changeCustomLineItemQuantity`). Fee lines have no recurrence (one-time).
8. Adding the same sku again (same offer, same custom fields) makes commercetools increase the existing line's quantity: allowed only for phone plans (cap 5); for any other kind answer 422 `OFFER_BLOCKED` kind `limit` reason `QUANTITY_FIXED`.

**`changeLineQuantity`:** validates against `QUANTITY_RULES` (phone plan 1-5; other plans 1; add-on follows parent; equipment 1; device 1-5), then `changeLineItemQuantity`; in the same update the dependents' quantities follow the parent (`add-on` lines with `parentLineItemId = line.id` get the same quantity; the fee custom line item gets the same quantity); equipment/device stock re-checked via `getAvailableQuantity`.
**`removeLine`:** collects dependents (`parentLineItemId === lineId`, plus the fee line `activation-fee:<offerKey>` if no other plan of that offer remains). Without `cascade` and with dependents -> throws `ApiError('HAS_DEPENDENTS', details.dependents)`; with `cascade: true` one update with `removeLineItem`/`removeCustomLineItem` actions for the line and all dependents (D-026: "removing the plan removes its dependents after confirmation").
**`normalizeCart(cart)`** (idempotent; the only function that fixes carts after a merge): (a) cap a phone plan quantity at 5; (b) re-link dependents whose `parentLineItemId` points to a line id that no longer exists: if exactly one plan line is a valid parent (guard `parentCandidates`) set it with `setLineItemCustomField`, otherwise leave it and let `revalidateCart` raise `ORPHANED_DEPENDENT`; (c) keep one fee line per offer with quantity = plan quantity; (d) never delete a line the buyer chose. Writes nothing (and returns the same cart object) when nothing is wrong.

### `lib/ct/availability.ts` (`server-only`) [SKILL: commercetools-platform]
`getAvailableQuantities(skus: string[]): Promise<Record<string, number>>`: one call `GET /inventory?where=sku in ("a","b")&limit=100` (never cached); a physical sku with no entry = 0; services are never queried (D-019): only lines of kind `equipment` and `device` are checked. `inStock = available >= quantity`. Used by `addOfferLine`/`changeLineQuantity` (409 `INSUFFICIENT_STOCK {available}`) and by `getMappedCart` to fill `line.stock` and raise issue `OUT_OF_STOCK` (blocking).

### `lib/mappers/cart.ts` — `mapCart(ct: CtCart, ctx: CartCtx, deps: { offers: Record<string, OfferFacts>; stock: Record<string, number>; issues: CartIssue[]; today: string }): Cart`
- `kind`/`family`/`technology`/`bullets`/`imageUrl` from `offers[offerKey]`; `offerKey` from the line custom field; custom line items: slug starting `activation-fee:` -> `kind 'fee'`, `chargeType 'one-time'`, `offerKey = slug suffix`, `parentLineId` = id of the first plan line of that offer.
- `termMonths` from the variant attribute `contract-term` of the sold sku (`termFromContractTerm`), device/Q lines may override later.
- `chargeType = line.recurrenceInfo ? 'recurring' : 'one-time'`; `recurrence` from `recurrenceInfo` (policy key from the expanded reference or `MONTHLY_POLICY_KEY` when the policy id equals the cached monthly policy id).
- `unitListPrice = line.price.value`; `total = line.totalPrice`; `unitPrice = total / quantity` (integer division only for display; `total` is authoritative); `appliedDiscountKeys` from `discountedPricePerQuantity`.
- `includedAtNoCharge = parent offer's includedAddonKeys contains offerKey && total.centAmount === 0`.
- `schedule`: plans only (`kind 'plan'` and `chargeType 'recurring'`): `buildSchedule({ offerKey, sku, termMonths, quantity, standing: unitListPrice, introApplied: appliedDiscountKeys.includes(discountKeyFor(introDef)), monthToMonth: <price of the offer's month-to-month recurring variant or null>, oneTimeDueNow: <fee line total of that offer>, orderDate: today })`; on `ok:false` the line gets issue `SCHEDULE_NOT_PRICEABLE` (`messageKey bundle.issue.scheduleNotPriceable`). `today` is the UTC date of the request; the PriceSchedule shows "dates assume you order today".
- `label`: plans only: `buildLabel(...)`; on `{ok:false}` the line gets issue `LABEL_DATA_MISSING`.
- `summary`: `monthly` = sum of `total` of lines with `chargeType 'recurring'`; `oneTime` = sum of `total` of one-time lines and fee lines; `plans`/`addons`/`devicesMonthly` = recurring subtotals by kind (`equipment` rentals count in `addons`); `total = ct.totalPrice`; `tax = ct.taxedPrice ? (gross - net) : null`; `discountTotal` = sum over lines of (`price x quantity` - `total`) plus `ct.discountOnTotalPrice?.discountedAmount`. All server-side sums of engine numbers; the client never adds money (cross-cutting rule).
- `discountCodes[]`: from `ct.discountCodes[].state`: `MatchesCart` -> `applied`; `DoesNotMatchCart` -> `not-applicable` (reason `not-applicable`); `NotActive` -> `not-active`; `NotValid` -> `not-valid`; `MaxApplicationReached` -> `max-reached`; `ApplicationStoppedByPreviousDiscount` and `ApplicationStoppedByGroupBestDeal` -> `stopped`. (A code can flip to `DoesNotMatchCart` after any line change: the mapper is the single place that reports it; scenario "Discount stops applying".) `code` is read from the expanded `discountCode.obj.code` (cart reads use `expand=discountCodes[*].discountCode`).
- `minimumOrder` from `lib/cart/minimum.ts`; `canCheckout = lines.length > 0 && no MINIMUM shortfall && issues.length === 0`; `checkoutBlockedBy` lists the reasons (`EMPTY`, `MINIMUM_ORDER`, `ISSUES`).
- `itemCount = lines.filter(l => l.kind !== 'fee').length`.
`lib/cart/minimum.ts`: `getMinimumOrder(currency): Money | null` (null when 0), `shortfall(total: Money, currency): Money | null` (`required - total` when `total < required`). Applied to the engine `total` (due today). The same function is exported for U (checkout route must enforce it too: "if the cart page enforces it but checkout does not, buyers will find the gap").

### Blocked-add contract (J and K verdicts -> UI) — exactly how a refused add is reported
`lib/cart/guard.ts` is the **only** file that imports J's and K's functions. Expected shapes (J and K own the real exports; **read their workstream files first; adapt only in `guard.ts`**; any difference is recorded in a `// ADAPTER:` comment):
```ts
// J (lib/offers/…): checkCompatibility(ctx, state, add) -> { allowed: boolean; reasons: Reason[] }; requiredEquipment(ctx, state, offerKey) -> { offerKey: string; sku: string }[]; revalidateCompatibility(ctx, state) -> Issue[]; parentCandidates(ctx, state, offerKey) -> string[] /* line ids */
// K (lib/offers/…): checkExclusivity(ctx, state, add) -> { allowed; reasons; replace?: { lineId; offerKey } }; checkEligibility(ctx, add) -> { allowed; reasons }; revalidateExclusivity / revalidateEligibility(ctx, state) -> Issue[]
// Reason = { code: string; messageKey: string; params?: Record<string, string | number>; offerKeys?: string[]; lineIds?: string[] }
export interface GuardLine { lineId: string; offerKey: string; sku: string; quantity: number; parentLineId: string | null }
export type GuardResult = { allowed: true; required: { offerKey: string; sku: string }[] } | { allowed: false; blocked: BlockedAdd };
export function guardAdd(input: { ctx: RuleContext; lines: GuardLine[]; add: { offerKey: string; sku: string; quantity: number; parentLineId: string | null } }): GuardResult;
export function revalidateCart(ctx: RuleContext, lines: GuardLine[]): CartIssue[];
```
`guardAdd` evaluates in this order and returns at the **first failing group** (all reasons of that group are returned): (1) M rules -> `kind 'invalid'|'limit'`: quantity out of `QUANTITY_RULES` (`QUANTITY_OUT_OF_RANGE`), non-phone quantity > 1 (`QUANTITY_FIXED`), `ONE_PLAN_PER_CATEGORY` (a different plan of the same category - cable, fixed-wireless or phone - is already in the bundle -> `kind 'conflict'` with `replace`); (2) K eligibility -> `kind 'ineligible'` (an ineligible offer is absent from listings; this is the server's defence, D-022: absolute, no override); (3) K exclusivity -> `kind 'conflict'` with `replace: { removeLineId, removeOfferKey }` taken from K's verdict (**symmetric**: K evaluates both directions); (4) J compatibility -> `kind 'incompatible'`; stock is checked by the route after the guard -> `kind 'unavailable'` `INSUFFICIENT_STOCK`.
`RuleContext` is built by `lib/cart/ruleContext.ts` (`server-only`): `{ offers: Record<string, OfferFacts-for-rules> /* H, cached by H */, customerGroup, channel: 'online', postalCode: cart.custom.postalCode, holdings: K getHoldings(customerId) /* signed-in only */, now }`.
**HTTP/JSON for a blocked add** (`POST /api/cart/line-items`):
| `blocked.kind` | HTTP | error `code` |
| --- | --- | --- |
| `incompatible`, `conflict`, `unavailable` | 409 | `OFFER_BLOCKED` |
| `ineligible` | 403 | `OFFER_BLOCKED` |
| `invalid`, `limit` | 422 | `OFFER_BLOCKED` |
Body: `{ "error": { "code": "OFFER_BLOCKED", "message": "<en text of the first reason>", "details": <BlockedAdd> }, "cart": <Cart> }` where `cart` is the unchanged current cart (so the UI re-renders from the server). The UI builds the text with `t(reason.messageKey, reason.params)` (J/K own those message keys and add them to **both** locale files); fallback key `bundle.blocked.generic`. For `kind: 'conflict'` the UI shows two buttons: **Replace {existing} with {new}** (re-sends the same POST with `replaceLineId = blocked.replace.removeLineId`; the server removes that line and its dependents and adds the new one **in one `withCartRetry` after re-running the guard against the cart without the removed lines**) and **Keep {existing}** (closes). The server re-checks everything on every add (scenario "Server re-checks what the card allowed" in J): the card's earlier verdict is never trusted.
**Rules that changed after the line was added** (J "Cart older than the rule", "Compatibility changes after the cart was built"; K "Conflict declared after the cart was built", "Location changes mid session", "Eligibility lost before checkout"): `getMappedCart` runs `revalidateCart` on **every read**; each issue becomes a `CartIssue` (`severity 'blocking'`, `messageKey` from J/K, `lineId`), shown in the `IssuesBanner` and next to the line; `canCheckout = false` while any exists. U must call `getMappedCart` and refuse to create the checkout session when `!canCheckout`.

### Routes (`app/api/cart/**`; every success **and every error that has a cart** returns the full mapped `Cart`)
Error shape: `{ error: { code, message, details? }, cart?: Cart }` (E's `ApiError` shape plus `details` and a sibling `cart`). All routes: read session (E), resolve `CartCtx` from the market cookie (D), never cache (`export const dynamic = 'force-dynamic'`).
| Route | Body / query | Success | Errors |
| --- | --- | --- | --- |
| `GET /api/cart` | none | `200 { cart: Cart \| null }` (normalizes, revalidates; a non-Active or other-currency cart clears `session.cartId` and returns `{ cart: null }`) | 503 `CART_ERROR` |
| `POST /api/cart/line-items` | `{ offerKey: string, sku: string, quantity?: number /* default 1 */, parentLineId?: string, replaceLineId?: string }` | `200 { cart }` (creates the cart on first add and writes `cartId` to the session) | 400 `INVALID_BODY`; 404 `UNKNOWN_OFFER`, `UNKNOWN_SKU`; 409/403/422 `OFFER_BLOCKED`; 409 `INSUFFICIENT_STOCK {available}`; 422 `RECURRING_PRICE_MISSING`, `SCHEDULE_NOT_PRICEABLE`, `LABEL_DATA_MISSING`, `PARENT_REQUIRED`; 409 `CART_CONFLICT` |

### Discount-activating prompt (`discount-activating-offer-prompt`, D-027)
- **Discounts** (seeded by M-15 with L's loader, `scripts/seed/data/cart-discounts/`): 
  - `malva-cd-second-line-10` "Second line $10 off": `cartPredicate: 'true'`, `target: { type: 'pattern', triggerPattern: [{ type: 'CountOnLineItemUnits', predicate: 'categories.key = "malva-cat-phone-plans"', minCount: 1, maxCount: 1 }], targetPattern: [{ type: 'CountOnLineItemUnits', predicate: 'categories.key = "malva-cat-phone-plans"', minCount: 1, maxCount: 1 }], maxOccurrence: 1, selectionMode: 'Cheapest' }`, `value: { type: 'absolute', applicationMode: 'IndividualApplication', money: [{ currencyCode: 'USD', centAmount: 1000 }, { currencyCode: 'EUR', centAmount: 900 }] }`, `sortOrder: '0.3'`, `stackingMode: 'Stacking'`, `requiresDiscountCode: false`, `isActive: true`. One trigger unit + one discounted unit = exactly "the second line".
  - `malva-cd-bundle-cable-phone-5` "Bundle with cable $5 off": `cartPredicate: 'lineItemExists(categories.key = "malva-cat-cable-internet") = true'`, same pattern target on phone units with `trigger: []` and `targetPattern` one unit, `maxOccurrence: 1`, `selectionMode: 'Cheapest'`, value absolute `IndividualApplication` USD 500 / EUR 450, `sortOrder: '0.4'`, `Stacking`.
  - `malva-cd-code-cable5` "$5 off Cable with code": `requiresDiscountCode: true`, `cartPredicate: 'lineItemExists(categories.key = "malva-cat-cable-internet") = true'`, `target: { type: 'lineItems', predicate: 'categories.key = "malva-cat-cable-internet"' }`, absolute USD 500 / EUR 450, `sortOrder: '0.5'`; plus the Discount Code `{ key: 'malva-code-cable5', code: 'MALVA-CABLE5', cartDiscounts: [{ typeId: 'cart-discount', key: 'malva-cd-code-cable5' }], isActive: true }` created by the same loader (M appends a `discountCodes` section to `scripts/seed/discounts.ts`: create when missing, `changeIsActive`/`changeCartDiscounts` when present).
  Category keys are the ones in ARCHITECTURE (`malva-cat-*`). Offers are products in these categories (D-010), so the predicates need no ids or SKUs. Verified field shapes: https://docs.commercetools.com/api/projects/cartDiscounts (pattern target, `applicationMode`), predicates page (`categories.key`, `lineItemExists`).
- **Pairings** (`lib/config/promptPairings.ts`, curated, **Planner default**; reviewed by the merchandiser monthly in a PR because v1 has no conversion analytics):
```ts
export interface PromptPairing { key: string; discountKey: string; messageKey: string; eligibleGroups?: ('consumer'|'small-business'|'employee'|'existing-customer')[]; when: (s: PromptState) => boolean; candidate: (s: PromptState) => { offerKey: string; termMonths: TermMonths; quantity: number } | null }
export const PROMPT_PAIRINGS: PromptPairing[] = [
  { key: 'bundle-cable-phone', discountKey: 'malva-cd-bundle-cable-phone-5', messageKey: 'bundle.prompt.cablePhone',
    when: s => s.hasCategory('malva-cat-cable-internet') && !s.hasCategory('malva-cat-phone-plans'),
    candidate: () => ({ offerKey: 'malva-offer-phone-essential', termMonths: 0, quantity: 1 }) },
  { key: 'second-line', discountKey: 'malva-cd-second-line-10', messageKey: 'bundle.prompt.secondLine',
    when: s => s.phoneLineCount() === 1,
    candidate: s => ({ offerKey: s.phoneOfferKey()!, termMonths: s.phoneTerm(), quantity: 1 }) },
];
```
  (`PromptState` is a small read-only view over the mapped cart: `hasCategory`, `phoneLineCount`, `phoneOfferKey`, `phoneTerm`.) The second pairing "adds a line" by increasing the phone plan quantity by 1 (never changes an existing line's offer: D-027).
- **Engine** `lib/pricing/prompts.ts` (`server-only`): `getPrompts(cart: CtCart, mapped: Cart, ctx, rule: RuleContext): Promise<DiscountPrompt[]>`. For each pairing, at most `PROMPT_MAX_CANDIDATES` (3) in config order:
  1. `when(state)` false -> skip ("No reachable discount": nothing is returned and nothing unrelated is promoted).
  2. **Satisfied:** if `attributable(mappedCart, discountKey) > 0` -> skip ("Satisfied discount not repeated").
  3. **Eligibility before pricing:** pairing `eligibleGroups` must contain the customer's group when set, and `guardAdd` (the same function the add route uses) must return `allowed` for the candidate on the current cart; otherwise skip ("Ineligible offer never suggested"; a pairing that would need a replace or a change to an existing line is skipped: prompts only suggest adding).
  4. **Price a prospective cart:** create a probe cart (`lib/ct/cartDrafts.ts` `buildProbeDraft(cart, candidate)`: same currency, country, locale, customerId or anonymousId, customerGroup, taxMode, inventoryMode, current lines (sku, quantity, custom fields, recurrenceInfo), current custom line items, current discount codes, plus the candidate line built by the same builder as a real add, `key: 'prompt-probe-<uuid>'`, `deleteDaysAfterLastModification: 1`), read it, **always delete it in `finally`** (`DELETE /carts/{id}?version=`; a failed delete is logged, the 1-day auto-delete is the safety net). Never reads the cart's stale totals.
  5. `saving = attributable(probe, discountKey) - attributable(current, discountKey)` where `attributable(cart, key)` = sum over lines of `discountedAmount.centAmount x quantity` of every `includedDiscounts` entry whose `discount.key === key` (monthly lines only). Because it is read from the **priced** prospective cart, best-deal selection and `StopAfterThisDiscount` suppression are already included. If `saving <= 0` skip ("Suggestion is honoured when taken" depends on this: the stated amount is exactly what the real add later produces, same function, same line shape).
  Result `{ pairingKey, discountKey, candidate: { offerKey, sku, name, quantity, termMonths }, saving, messageKey, params: { name, saving: fmt(saving) } }`.
- **Never cached** (D-027): re-priced on every `GET /api/cart/prompts`. Cost: at most 3 probe carts (create + delete) per call; the client calls it once per cart version.
- **UI** `DiscountPrompts.tsx`: card (`pink-50` background, `--radius-lg`) titled "Save {saving}/mo" + the pairing sentence + pill button "Add" (`bundle.prompt.add`) that calls `addLine({ offerKey, sku, quantity })`; after success the prompt disappears because the discount is now satisfied. The saving is always an amount (scenario "Saving is quantified").
- **The three open questions (Planner defaults):** (1) *who curates pairings* -> the merchandiser, by changing `lib/config/promptPairings.ts` and the matching Cart Discount in a PR, reviewed monthly; (2) *how stale may a cached saving be* -> not at all: nothing is cached, every request reprices; (3) *suggest changing an existing line?* -> never: prompts only add a line (D-027) and are skipped when the guard would need a replace.

### Pitfalls
- Every cart update returns a new version; always render from the returned cart (never patch). `withCartRetry` re-reads, never reuses an old version; two tabs editing the same cart must both succeed (second retries once).
- `addLineItem` of an existing sku+custom merges into that line; the guard must count quantities, not lines.
- A recurring line whose variant has no price tied to `malva-monthly` is silently charged the one-time price: the add is rejected (`RECURRING_PRICE_MISSING`).
- Merged anonymous lines can get new ids: `parentLineItemId` can dangle -> `normalizeCart` re-links or flags `ORPHANED_DEPENDENT`. Fee custom line items can duplicate on merge.
- Discount codes flip to `DoesNotMatchCart` after any line change; read `discountCodes[].state` after **every** mutation (the mapper does).
- Cart discounts recalc on each update: totals are the engine's only; `monthly + oneTime` can differ from `total` once shipping or tax exist (hence the separate `dueToday`).
- Probe carts (prompts) are real carts: always delete in `finally`; they carry `deleteDaysAfterLastModification: 1`.
- Do not read the cart in the root layout (makes the site dynamic); the header pill is client-side.
- `Intl` dates in UTC (`timeZone: 'UTC'`), or de-DE users near midnight see shifted dates.
- Label CSS must not use tokens or inherit `font-family`; `all: initial` on the root is not used (it breaks the table layout); set the properties explicitly.
- Inventory is checked only for equipment and devices (D-019); services have no InventoryEntry.
- Hydration: the bundle page passes `initialCart` as the SWR fallback; the pill renders the same text server and client until SWR resolves.
