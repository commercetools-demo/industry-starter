## Context

> **Superseded in part by workstream T2 (decision D-055, 2026-11-05).** The Shopper MCP is removed. The backend is `StorefrontApiBackend` over the storefront's own modules (`lib/ct/*`, `lib/mappers/*`), built with the shopper's cookie session. The assistant's cart is the shopper's bag: there is no second cart and no adopt step. The current requirements are in `specs/shopping-assistant-storefront-backend/`, which replaces `specs/shopping-assistant-shopper-mcp/`. Where the text below names the Shopper MCP, the storefront modules are meant. This document is kept as the record of the T decisions.

Upstream is the specification (skill `shopping-agent` at `.claude/skills/shopping-agent/`, references `porting.md`, `backend.md`, `runtime.md`, `ui.md`, `verification.md`). A clone for reading lives wherever the junior puts it (never inside the repo); `docs/safety.md` is read in full before coding.

The storefront is Next.js 16 with a BFF chain (component, SWR hook, Route Handler, `lib/ct`), a signed `malva-session` cookie (HS256, 30 days) that holds `customerId`, `cartId`, `anonymousId`, `country`, `locale`, brand in the URL, Netlify hosting (D-038), in-memory rate limits.

## What the Shopper MCP gives us (documentation read 2026-11-04, preview docs)

Eight tools: `search_catalog`, `lookup_catalog` (≤ 20 ids), `get_product`, `create_cart`, `get_cart`, `update_cart` (**full replacement** of line items), `cancel_cart`, `get_order` (id **or order number**). Server pinned to one Store, country, locale, currency, distribution and supply channels. Amounts are integer minor units. Cart `item.id` is the variant SKU. Errors arrive as a normal tool result `{messages:[{type:"error", code, severity, path, content}]}`; codes `not_found`, `line_item_not_orderable`, `invalid_cursor`, `catalog_unavailable`. HTTP transport, `Authorization: Bearer`. Auth modes `ClientCredentials` (static token up to 30 days, or OAuth client-credentials discovery) and a shopper-identity mode whose behaviour the page does not describe.

**Not documented** (spike T-01 settles each against the live server and records fixtures): U1 input/output JSON schemas and required fields; U2 search filter names (category, price); U3 whether results carry images, slug, availability, attributes; U4 how a multi-variant product is identified (product id vs variant id); U5 `search_catalog` default and maximum page size; U6 whether `update_cart` accepts an empty list; U7 `totals[].type` values (discount, shipping, tax?); U8 line status values on orders; U9 what `get_order` returns for another customer's order under the token we hold; U10 cart ownership (can any caller read any cart id); U12 how a cart created by the MCP looks to the storefront (store reference, `shippingMode`, `taxMode`, `anonymousId`/`customerId`, line custom fields, `deleteDaysAfterLastModification`), read back read-only after `create_cart`.

## Goals / Non-Goals

**Goals:** catalogue discovery, a cart the assistant can edit, retrieval of the shopper's own past orders, all through the Shopper MCP; every safety rule of the reference preserved; one codebase for both brands and both markets.

**Non-Goals:** ordering, payment, address or shipping choice, discount codes, policies, memory, personalisation, order changes, returns.

## Decisions

**D1. Port module by module, keep upstream names.** Directories `lib/agent/common/` (role independent: fencing, streaming, presentation, prompt-assembly, grounding, execution, turn, skills, config, types, testing) and `lib/agent/shopping/` (backend, types, config, prompt, fencing, gates, grounding, enrichment, serialization, executor, tools). Files keep the upstream copyright line, `SPDX-License-Identifier: Apache-2.0` and a one-line "Adapted from `<upstream path>`; changes: ..."; licence text in `storefront/third_party/commerce-agents/LICENSE`, paths in `storefront/NOTICE`. Prompt text, tool descriptions, gate messages and the five-skill bodies are copied verbatim.

**D2. The backend is the Shopper MCP and nothing else.** `lib/agent/backend/shopper-mcp/` holds the MCP client, id scheme, money module, mappers and the `StorefrontBackend` implementation. No `lib/ct/*` or `@commercetools/*` import in `lib/agent/**` (lint-enforced). The agent core never sees a token; the host resolves URL and bearer token from the session market.

**D3. Tool surface by config, not by editing the builder.** `enable_cart: true`, `enable_orders: true`, `enable_policies: false`, `enable_fulfillment: false`, `enable_memory: false`, `enable_disclosures: false`, `enable_web_search: false`. `get_orders` stays in the tool list (upstream shape) and is served as described in D7. Presentation tools are all kept (including `present_plan`, `present_guide`) so the byte pin on the upstream render is unchanged; the UI builds all six cards. Skills installed: `search-discovery`, `purchase-research`, `planning-goals`, `customer-care`. `memory-personalization` is not installed (memory off). `purchase-research` and `customer-care` mention `search_policies`; they are written to say "when the terms do not address the question, say so" and stay byte-for-byte.

**D4. Id scheme (finalised after T-01).** Default assumption from the docs: the id the MCP returns for a plain product equals its variant SKU. A product with more than one variant is a *family*; its id is prefixed `fam:` in our namespace and is **refused by every cart write** (the options hold). A variant is addressed by its SKU. Encode/decode live in one module `ids.ts`; decoding never throws (unknown string = SKU). If T-01 shows that the MCP surfaces every variant as its own product, the family branch stays implemented but unreachable and the test asserts that.

**D5. Money.** MCP amounts are integer minor units. The agent domain is a float in major units. One inbound module `money.ts` converts using the currency's fraction digits (`Intl.NumberFormat(...).resolvedOptions().maximumFractionDigits`), never `/100`. A line's unit price is `lineTotal / quantity` computed in minor units. The checkout card receives a separate cent-exact payload built from the MCP cart `totals` (type `total`), displayed with the app's own `formatMoney(centAmount, currency, locale)`. Upstream's `formatMoney` is never copied.

**D6. The assistant cart is adopted as the storefront bag (owner decision Q-T-1, 2026-11-04).** The assistant creates and edits a cart through the MCP; its id is held server-side in the agent session (`agentCartId`, never sent to the browser or the model). Because `update_cart` replaces all lines, edits are read-modify-write under a per-session mutex (first add uses `create_cart`). When the shopper presses "Continue in my bag", the card calls a **new storefront API**, `POST /api/assistant/adopt-cart`, which sets that cart id as `cartId` in the signed `malva-session` cookie, so the normal bag, mini-cart and hosted Checkout work on it with no re-adding. The cart id comes only from the server-side agent session, never from a request body or a tool argument (a cart id is a credential: the MCP documents no ownership check).

The storefront only accepts carts it recognises (`ownsCart`, `shippingMode Single`, `taxMode Platform`, a shipping country, per-line custom fields `fulfilment` and `brand`). So adoption is `lib/ct/adopt-cart.ts` (existing BFF chain, existing `apiRoot`, existing `updateWithRetry`), in this order:
1. Read the cart. Refuse (named error, no session change) unless `cartState` is `Active`, currency and country equal the session market, and it has lines.
2. **Ownership**: the cart must carry neither `anonymousId` nor `customerId` (a cart already owned by someone else is refused). Then set the session's owner: `setCustomerId` for a signed-in shopper, otherwise `setAnonymousId` (the `ensureAnonymousId` value).
3. Normalise: `setShippingAddress {country}`, `setDeleteDaysAfterLastModification 30`, and one `setLineItemCustomType` per line with `fulfilment = delivery` and `brand` resolved by the existing brand/selection code (a drinks line carries the drinks brand and channel handling of the multibrand change). If the cart's `shippingMode` is not `Single` or `taxMode` is not `Platform` (not changeable in place), use the **fallback**.
4. **Fallback** (also used when the shopper's current bag is not empty, so no existing bag line is lost): re-add each line through the existing `addLine`, as `rebuildCart` does, into the existing bag (or a new cart), report dropped lines, then cancel the assistant cart via the MCP.
5. Write `cartId` to the session cookie (the route sets it with the same attributes as every other writer), clear `agentCartId`, revalidate the bag cache keys.

This is a deliberate, owner-approved use of the storefront's own commercetools code for adoption only. The agent core and the backend still call nothing but the Shopper MCP.

**D7. Orders.** The MCP has `get_order` only (by id or number); there is no "list my orders" and no documented customer scoping. So: order tools exist only for a **signed-in** shopper; before any `get_order` call the host checks that the order number is the shopper's through the storefront's existing, already customer-scoped account read (`getCustomerOrderByNumber(customerId, number)`), and an order that is not theirs is answered "not found", indistinguishable from an unknown number. `getOrders(limit)` returns the shopper's most recent order numbers from the same existing read, then details via `get_order`. Default is switchable (Q-T-2): off means the shopper must type an order number and ownership is whatever spike U9 proves.

**D8. One MCP server per market.** The server is pinned to a Store, country, locale and currency, so US and Canada are two servers; env `SHOPPER_MCP_URL_US|CA`, `SHOPPER_MCP_TOKEN_US|CA`. The agent session records the country at start; a market change ends the agent session and the assistant cart. Brands are **not** separable at the MCP (no brand in the output, selections are not exposed), so the assistant sells both brands; scoping to the page brand is a follow-up (Q-T-3).

**D9. Session storage.** Netlify Blobs: a small state document (principal, provenance array, `agentCartId`, version) written with `onlyIfMatch` etag, and the transcript as an append log. The module-level `Map` implementation exists for tests and `next dev` only and refuses to construct when `NODE_ENV=production`.

**D10. Transport and the host ceiling.** Phase 0 decides SSE vs buffered on a real Netlify deploy. Settings for a 60 s ceiling: request timeout 40 s, max tool iterations 4, provenance cap 60, turn deadline 48 s (checked between rounds). Session is persisted immediately before `turn_complete`. No background work (memory is off, so there is no extraction route).

**D11. Session start resolves identity and cart before the stream.** `POST /api/assistant/session` (plain JSON) binds the principal from the signed cookie, mints the agent session id, writes it into `malva-session` as `agentSessionId` (new key in `SESSION_KEYS`; mind `MAX_TOKEN_LENGTH`), and returns only `{ready:true}`. Every cookie write passes the same attributes as the rest of the storefront.

**D12. UI.** Copy `protocol.ts`, `turn.ts`, `scroll.ts`, `api.ts` (event reader), `Markdown.tsx`, `QuotedAsData.tsx`, `MessageBubble.tsx`, `Suggestions.tsx`, `Transcript.tsx`, `Composer.tsx`. Do not bring `ui.tsx`, `icons.tsx`, `catalog.ts`, `formatMoney`. One scoped token layer maps the reference custom properties onto Malva tokens (`app/tokens.css`), imported in the Tailwind base layer. Cards are drawn at panel width (480 to 560 px) with container queries. Showcase page renders every card, slot state and locale from fixtures.

**D13. No invented facts on cards.** Upstream's sparkline and sentiment bars are deleted. Rating, review count, stock, delivery estimate and tracking are shown only if the MCP supplied them (U3, U8); otherwise absent.

## Risks / Trade-offs

- **MCP has no optimistic concurrency on carts** and `update_cart` replaces: two parallel writes from two serverless instances can lose a line. Mitigation: per-session mutex (one process), `Retry` after read-back verification (re-read the cart after write; if the line is missing, retry once), documented residual risk.
- **Order ownership depends on a storefront read**, which is an extra commercetools call (Q-T-2, owner accepted the default). The **adopt-cart** route is a second one (Q-T-1, owner decision).
- **Tokens expire** (static bearer max 30 days): the host maps a 401 from the MCP to a named `assistant_unavailable` error and logs one line; owner row OA-T-b records the expiry date. OAuth client-credentials discovery is the follow-up.
- **Preview docs.** Names and shapes may change; the contract tests run on recorded fixtures plus one opt-in live test (`npm run test:live`).
- **Cost.** Every turn is a paid model call and the routes are reachable by anonymous callers: same-origin check, per-class rate limits, an Anthropic spend cap (OA-T-d). The rate limiter is per instance and is not a spend control.
- **Prompt bytes are frozen** (D3): changing a config switch later costs one cache rebuild; pinned by test.
